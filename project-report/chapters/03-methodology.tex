% \label{subsec:functional_requirements}

% The functional requirements describe the end-to-end behaviour of the pipeline.
% The system takes as input a single broadcast football video and produces, for
% each frame, a set of per-object detections, persistent track identities, team
% labels, pitch-coordinate positions, and a collection of derived tactical
% outputs. The requirements are decomposed by pipeline stage so that each
% subsequent section of this chapter can be mapped directly to the requirement
% it satisfies.

% \paragraph{FR1: Object detection.} The system shall detect the four classes
% relevant to broadcast football analysis---players, goalkeepers, referees, and
% the ball---in each frame of the input video, returning axis-aligned bounding
% boxes and class labels. Given the extreme scale disparity between outfield
% players and the ball, detection of the ball shall be handled by a dedicated
% model operating at the same input resolution but with its own training regime
% and confidence regime, rather than relying on the generic detector alone.

% \paragraph{FR2: Multi-object tracking.} The system shall maintain consistent
% identities for detected players, goalkeepers, and referees across frames,
% associating detections over time into persistent tracks. Tracker choice shall
% be configurable so that alternative association strategies can be compared.
% Ball identity is not required to persist, since the ball is a single object
% and its per-frame localisation is sufficient for downstream use.

% \paragraph{FR3: Team identification.} The system shall assign each tracked
% player to one of two teams without manual labels, using visual appearance
% alone. The assignment shall be stable over time: transient misclassification
% on a single frame shall not be allowed to propagate as the team label returned
% for a track. Goalkeepers, whose kits typically differ from their outfield
% teammates, shall be resolved to a team by a separate mechanism rather than
% being forced into the outfield clustering.

% \paragraph{FR4: Pitch registration.} The system shall recover the planar
% homography between the broadcast image and a canonical pitch model, permitting
% image-plane coordinates to be mapped to pitch-plane coordinates. Registration
% shall tolerate the fact that the full pitch is rarely visible in a broadcast
% frame, and shall degrade gracefully when insufficient correspondences are
% available in a given frame by reusing the most recent valid transform until a
% new valid estimate is obtained.

% \paragraph{FR5: Tactical output generation.} From the projected per-track
% trajectories the system shall derive a set of tactical outputs: per-player
% heatmaps of pitch occupation, speed and distance statistics, team possession,
% pass events, and offside candidate frames. Each output shall be produced in
% pitch coordinates, so that the reported quantities are physically meaningful
% rather than tied to the broadcast view.

% \paragraph{FR6: Visualisation and persistence.} The system shall render the
% principal outputs for inspection---annotated broadcast video with detection,
% track, and team overlays; a bird's-eye projection of tracked objects onto the
% pitch model; and rendered heatmaps---and shall persist these together with any
% per-frame numerical outputs so that results can be reviewed offline and used
% as input to the evaluation procedure.

% The non-functional requirements describe qualities the system should exhibit
% irrespective of the specific outputs it produces.

% \paragraph{NFR1: Reproducibility.} The full configuration required to
% reproduce a given run---model weights, parameter values, and preset
% selections---shall be recoverable from a single set of launch arguments, and
% the training of any bespoke models shall be recorded with sufficient detail
% (dataset, hyperparameters, training curves) to be repeated by a peer.

% \paragraph{NFR2: Modularity.} Each pipeline stage shall be implemented as a
% self-contained component with a clearly defined input and output contract, so
% that an individual stage can be replaced, reconfigured, or evaluated in
% isolation without requiring changes to the surrounding system.

% \paragraph{NFR3: Configurability.} Parameter values that govern behaviour at
% runtime---detection thresholds, tracker selection, inference strides, warmup
% sizes, smoothing windows, displacement gates---shall be exposed through the
% command-line interface rather than embedded in source code, and reasonable
% defaults shall be provided in a single location so that the system can be run
% without a long argument list.

% \paragraph{NFR4: Robustness to broadcast artefacts.} The pipeline operates on
% broadcast video rather than instrumented capture, and must therefore tolerate
% partial occlusion, motion blur, pan-tilt-zoom camera motion, and the
% appearance of on-screen graphics without catastrophic failure. Robustness is
% treated as a design objective at each stage rather than as a single global
% property, with appropriate mechanisms (temporal smoothing, displacement gates,
% majority-vote filtering) introduced where individual stages are known to be
% sensitive.

% \paragraph{NFR5: Graceful degradation.} When an individual stage cannot
% produce a usable output for a given frame, the pipeline shall continue to
% operate on subsequent frames rather than terminate. For pitch registration in
% particular, the system shall retain the most recent valid homography and
% reuse it until a new valid estimate is produced. The extent to which other
% stages meet this objective is discussed alongside the relevant component.

% \paragraph{NFR6: Inspectability.} Intermediate outputs of the pipeline---raw
% detections, tracked identities, projected positions, registration overlays,
% per-track statistics---shall be exposable for inspection, so that failure
% modes can be localised to specific stages during development and evaluation,
% and so that the evaluation procedure can assess each stage independently.

% \paragraph{NFR7: Runtime.} The pipeline is intended for offline post-match
% analysis rather than real-time or live operation. Runtime is therefore not a
% primary design objective: the system shall complete processing of a broadcast
% clip on a single consumer GPU within a reasonable working session, but no
% throughput target is set, and design decisions throughout the pipeline
% prioritise per-stage accuracy and inspectability over end-to-end speed. The
% measured processing cost and the stages that dominate it are discussed
% alongside the results in Chapter~\ref{ch:evaluation}.

% The left branch handles \emph{what} is in the frame: objects are detected,
% outfield actors are tracked over time, and each tracked player is assigned
% to a team. The right branch handles \emph{where} the frame sits in
% pitch-space: canonical landmarks on the pitch are detected and resolved
% into a planar homography. The two branches are independent---no stage in
% one depends on an output of the other until they converge---and this
% independence is exploited at runtime, since pitch keypoints change slowly
% relative to player positions and the right branch is therefore executed at
% a lower frequency than the left.

% \paragraph{Models and rule-based components.} The appearance stages are
% fully model-based. A generic YOLO detector is run on each frame and
% produces bounding boxes for players, goalkeepers, and referees; a second
% YOLO detector dedicated to the ball is run in parallel on the same frame
% and is the authoritative source of ball localisation (the ball-class
% outputs of the generic detector are discarded, for reasons given in
% Section~\ref{sec:detection_tracking}). Pitch landmarks are produced by a
% keypoint model. The team identification stage combines a pretrained
% vision-language embedding model (SigLIP) with dimensionality reduction
% (UMAP) and a small unsupervised clustering step (k-means, $k=2$). The
% tracker is a learning-free multi-object association algorithm (ByteTrack,
% with BoT-SORT selectable) applied to the generic detector's player,
% goalkeeper, and referee outputs only; the ball is never passed to the
% tracker and instead passes through a lightweight temporal filter (nearest
% neighbour to the previous accepted position under a displacement gate)
% described in Section~\ref{sec:detection_tracking}. All stages downstream
% of projection---heatmap accumulation, speed and distance computation,
% possession, pass detection, offside geometry---are rule-based: they
% operate deterministically on projected trajectories and carry no learned
% parameters.

% \paragraph{Caching and stride.} Two caching mechanisms are used to control
% the per-frame computational cost. First, pitch keypoint inference is run
% once every \texttt{pitch-stride} frames (default 15) and the resulting
% homography is reused on intervening frames; when a new inference fails to
% produce a valid estimate, the last valid homography is retained. Second,
% team classification is fitted once during a warmup window at the start of
% the video (default 20\,s in the production preset) and reused thereafter;
% per-track team labels are produced by applying the fitted classifier to
% new crops and are stabilised by a majority-vote smoother over a 30-frame
% window. No other stage caches state across frames beyond the track state
% held internally by the tracker.

% \paragraph{Execution model.} The pipeline is driven by a single
% orchestration loop in \texttt{src/pipeline/run.py} that reads frames
% sequentially, invokes the stages in the order shown in
% Figure~\ref{fig:pipeline_architecture}, and writes outputs to disk. The
% loop is deliberately sequential rather than concurrent: the stages have
% strict data dependencies, intermediate outputs are required for
% inspection and evaluation (NFR6), and real-time operation is explicitly
% out of scope (NFR7).

% \paragraph{Detection and tracking record.} The core data object in the left
% branch is \texttt{supervision.Detections} with four populated fields. A
% raw detection set $\mathcal{D}$ of $N$ objects carries $\mathbf{B} \in
% \mathbb{R}^{N \times 4}$ for bounding boxes in absolute pixel coordinates
% $(x_1, y_1, x_2, y_2)$, $\mathbf{c} \in [0,1]^N$ for per-detection
% confidences, and $\mathbf{k} \in \{0,1,2,3\}^N$ for class identifiers
% under the detector's label set $\{0\!:\!\mathrm{ball},\,
% 1\!:\!\mathrm{GK},\, 2\!:\!\mathrm{player},\, 3\!:\!\mathrm{referee}\}$.
% The tracker additionally populates $\mathbf{t} \in \mathbb{Z}^N$ with
% integer track identifiers on frames where association has succeeded; on
% frames where the tracker has produced no identifier, this field is
% absent.

% \paragraph{Encoding of team membership.} Team membership is encoded by
% overwriting the \texttt{class\_id} field in place rather than by adding a
% new field to the detection record. Following team assignment, the
% semantics of \texttt{class\_id} change: outfield players carry
% $\mathrm{class\_id} \in \{0, 1\}$ denoting team A or team B, goalkeepers
% are resolved to the same two-valued alphabet where possible and to the
% value $2$ otherwise, and referees are forced to $2$. This reinterpretation
% is deliberate: downstream renderers and exporters consume the field
% uniformly as a palette index, and the reuse avoids maintaining two
% parallel arrays that must be kept in lockstep. It is documented here
% explicitly because the value $2$ denotes \emph{referee or unresolved
% goalkeeper} after team assignment, not \emph{player} as in the raw
% detector output.

% \paragraph{Ball as a distinct data stream.} The ball is handled as a
% separate \texttt{supervision.Detections} instance throughout the pipeline.

% \texttt{tracker\_id}, and is consumed by downstream stages (bird's-eye
% render, offside detector, stats tracker) as a parallel argument alongside

% \section{Small-Object Detection and Dedicated Ball Detection}
% \label{sec:background_ball_detection}
 
% Although the ball is the primary object of interest in football, it is also
% the hardest to detect reliably in broadcast footage. At typical broadcast
% resolution, the ball subtends only a few dozen pixels in diameter, moves
% rapidly enough to produce motion blur, and is frequently occluded by players
% or absent from the frame entirely~\cite{Gualtieri2023}. These properties
% place it firmly in the small-object detection regime, where standard
% detectors trained jointly on all classes tend to underperform because larger,
% more visually prominent objects dominate the training
% signal~\cite{Theiner2022}.
 
 
% \subsection{Why Small Objects Are Harder to Detect}
% \label{subsec:background_small_object_difficulty}
 
% The COCO benchmark defines a small object as one whose bounding box occupies
% fewer than $32 \times 32$ pixels~\cite{lin2014microsoft}. By this standard,
% the ball in a wide-angle broadcast frame is consistently small, often below
% $20 \times 20$ pixels depending on camera zoom.
 
% Small-object detection is inherently harder for two reasons. First, the IoU
% criterion (Equation~\eqref{eq:iou}) becomes disproportionately sensitive to
% localisation error at small scales: a fixed pixel displacement $\delta$
% produces a much larger IoU drop on a small box than on a large one. As shown
% in Figure~\ref{fig:iou_degradation}, a 2-pixel shift reduces IoU from 1.0 to
% 0.78 on a $16 \times 16$ box but only to 0.94 on a $64 \times 64$ box. This
% makes ball detection acutely sensitive to blur, noise, and detector
% uncertainty. Second, in convolutional architectures the spatial resolution of
% feature maps decreases with depth; by the deepest layers, small objects may
% occupy only a single cell or be lost entirely. The FPN neck described in
% Section~\ref{subsec:background_yolo} partially mitigates this, but the
% representation of very small objects remains inherently weaker than that of
% larger ones~\cite{lin2017feature}.
 
% \begin{figure}[!htbp]
%     \centering
%     \includegraphics[width=0.75\linewidth]{images/iou_degradation.png}
%     \caption{Effect of pixel displacement $\delta$ on IoU for square
%         bounding boxes of varying size. A single-axis shift is applied to
%         the predicted box while the ground-truth box remains fixed. At
%         $\delta = 2$ pixels, a $16 \times 16$ box drops to
%         $\mathrm{IoU} = 0.78$ while a $64 \times 64$ box retains
%         $\mathrm{IoU} = 0.94$, illustrating why small-object detection is
%         disproportionately sensitive to localisation error. The dashed line
%         marks the standard $\mathrm{mAP}_{50}$ threshold.}
%     \label{fig:iou_degradation}
% \end{figure}
 
 
% \subsection{Strategies for Small-Object Detection}
% \label{subsec:background_small_object_strategies}
 
% Several strategies have been proposed to address these difficulties.
% Multi-scale detection heads, as used in FPN-based architectures, are the most
% widely adopted architectural response; some methods extend this with
% additional high-resolution prediction scales or dilated
% convolutions~\cite{lin2017feature}. At the data level, augmentation
% techniques such as copy-pasting small object instances into new training
% locations improve recall on under-represented size
% categories~\cite{kisantal2019augmentation}, while inference-time tiling
% increases effective resolution at the cost of higher computation.
 
% A complementary approach is to train a dedicated detector whose capacity,
% input resolution, and confidence thresholds are tuned specifically for the
% small-object class. This avoids the class-imbalance problem inherent in
% joint training and allows the operating point to be optimised independently.
% In particular, operating at a low confidence threshold $\tau$ maximises
% recall at the cost of increased false positives — a trade-off that can be
% managed by downstream temporal filtering rather than within the detector
% itself~\cite{Gualtieri2023}.
 
 
% \subsection{Temporal Filtering of Ball Candidates}
% \label{subsec:background_temporal_filtering}
 
% When a detector operates at a low confidence threshold, the resulting
% candidate set at each frame contains both the true ball and spurious
% detections. The general form of this set at frame $t$ is
% \begin{equation}
%     C_t = \left\{\bigl(\mathbf{b}_t^{(j)},\, s_t^{(j)}
%            \bigr)\right\}_{j=1}^{N_t},
%     \label{eq:ball_candidates}
% \end{equation}
% where $\mathbf{b}_t^{(j)}$ is a candidate location and $s_t^{(j)}$ its
% confidence score.
 
% Temporal coherence provides a principled basis for disambiguation. Because
% the ball follows a physically continuous trajectory, its inter-frame
% displacement is bounded even under rapid motion. Two families of filtering
% exploit this property. Motion-model approaches, such as the Kalman filter
% described in Section~\ref{subsec:background_tracking_by_detection}, predict
% the ball's next position using an explicit dynamical model and select the
% closest candidate. These are effective when the assumed model holds, but can
% diverge under the abrupt accelerations from kicks, deflections, and rebounds
% that are routine in football. An alternative family enforces only that
% inter-frame displacement remains below a physically plausible bound,
% discarding candidates that would imply impossible ball speeds regardless of
% confidence. This sacrifices predictive power during smooth motion but is more
% robust to the sharp trajectory changes characteristic of ball dynamics.
 
% The choice between these families, and the specific instantiation used in
% this project, is discussed in Chapter~\ref{ch:methodology}.
% Chapter~\ref{ch:evaluation} reports ball detection performance separately
% from the general object detector.

% The tracking stage is vulnerable to several common failure cases. Occlusion can
% cause a player to disappear temporarily, leading to a broken track. Similar
% player appearance can cause identity switches, particularly when players cross
% or cluster around the ball. Camera motion can also affect the apparent movement
% of detections and make association more difficult.

% The pipeline mitigates these issues in two ways. First, the tracker itself

% \subsection{Warm-up Sampling and Player Cropping}
% \label{subsec:warmup_sampling_player_cropping}

% Team identification begins with a warm-up phase at the start of each video.
% During this phase, frames are sampled from the first 20 seconds of footage using
% a stride of 30 frames. The main detector is applied to these sampled frames, and
% only detections classified as players are retained. Very small crops are
% discarded using a minimum bounding-box size of 35 by 35 pixels, since such
% detections usually contain too little visual information for reliable team
% assignment.

% For each retained player detection, the system extracts a torso crop rather
% than using the full bounding box. The crop is taken from approximately 15\% to
% 65\% of the bounding-box height. This focuses the representation on the shirt
% region, which usually contains the strongest team-specific visual signal, while
% reducing noise from shorts, legs, grass, and nearby players. A maximum of 800
% warm-up crops is used, and at least 50 crops are required before the classifier
% is fitted.

% \subsection{Embedding and Clustering}
% \label{subsec:embedding_clustering}

% The retained torso crops are used to fit a team classifier. The classifier
% extracts visual embeddings from each crop using a SigLIP-based image encoder,
% then reduces the embedding dimensionality using UMAP and clusters the reduced
% representations using K-means with \(k=2\). The two clusters correspond to the
% two outfield teams.

% This approach was selected because it avoids requiring labelled team examples
% for every new match. A supervised team classifier would need new annotations
% whenever kits, lighting conditions, competitions, or broadcast styles changed.
% By fitting the classifier from the input video itself, the system can adapt to
% the visual appearance of the teams in the current match.

% During the per-frame pipeline, each tracked player crop is passed through the
% same embedding and clustering pipeline to obtain a predicted team label. The
% output is a binary team assignment for outfield players. These assignments are
% then stabilised using temporal smoothing before being used by downstream
% analytics.

% \subsection{Temporal Smoothing and Role Handling}
% \label{subsec:temporal_smoothing_role_handling}

% Frame-level team predictions can fluctuate because of occlusion, motion blur,
% partial crops, lighting variation, or players turning away from the camera. To
% reduce this instability, the system applies track-level majority-vote smoothing.
% For each track identifier, the most recent team predictions are stored in a
% fixed-length history of 30 predictions. The smoothed team label is then taken as
% the majority label within this history.

% This design reduces the effect of isolated incorrect predictions while still
% allowing the team label to update if a track was initially misclassified.
% Smoothing is especially important because team labels are used in later
% components where a single-frame error can affect possession, pass, or offside
% logic.

% Goalkeepers and referees require separate handling. Referees are assigned to a
% non-team class because they do not contribute to team possession or offside
% analysis. Goalkeepers are detected as a separate object class and are assigned
% to the team whose outfield-player centroid is nearest in image space. This
% spatial rule is used because goalkeeper kits often differ from the outfield
% players' kits, making appearance-based clustering less reliable for this role.

% The resulting representation assigns each detection either to team 0, team 1,
% or a non-team class. This representation is used consistently by the
% visualisation, possession, pass, and offside modules.

% \section{Pitch Registration}
% \label{sec:method_pitch_registration}

% Pitch registration maps image-space detections from the broadcast frame onto a
% canonical football pitch. This stage is required because image coordinates are
% affected by camera position, zoom, and perspective distortion. Tactical outputs
% such as heatmaps, speed, distance, possession proximity, and offside candidate
% detection therefore need to be computed in pitch space rather than directly in
% the broadcast image.

% \subsection{Pitch Keypoint Detection}
% \label{subsec:pitch_keypoint_detection}

% Pitch landmarks are detected using a YOLOv8x-pose model trained to localise 32
% canonical pitch keypoints. For each processed frame, the model predicts a set
% of keypoint coordinates and confidence scores. Keypoints with confidence below
% 0.5 are discarded before homography estimation. This filtering step reduces the
% effect of uncertain keypoint predictions, which can otherwise produce unstable
% or incorrect pitch transformations.

% A homography is estimated only when at least six valid keypoints are available.
% Although four point correspondences are theoretically sufficient to estimate a
% homography, requiring more than four points makes the transformation less
% dependent on any single detected landmark. Frames with too few reliable
% keypoints reuse the most recent valid transformation where possible, rather
% than forcing an unstable new estimate.

% \subsection{Homography Estimation and Coordinate Transformation}
% \label{subsec:homography_coordinate_transformation}

% For each valid set of pitch keypoints, the system estimates a homography
% between the detected image-space landmarks and their corresponding locations on
% a canonical pitch model. The homography provides a projective transformation
% from image coordinates to pitch coordinates. Once this transformation is
% available, detected object positions can be expressed in pitch space.

% For players, goalkeepers, and referees, the image-space position is taken as
% the bottom-centre point of the bounding box, since this approximates the point
% where the player contacts the ground. For the ball, the centre of the bounding
% box is used. These points are then transformed into pitch coordinates using the
% estimated homography.

% The pitch coordinate system is represented in centimetres, with a pitch length
% of 12,000 cm. Using metric-like pitch units allows later stages to express
% distance thresholds and spatial rules in interpretable terms. For example, the
% possession and offside modules use distances in centimetres rather than pixel
% distances, making the thresholds less dependent on camera zoom.

% \subsection{Caching and Robustness Measures}
% \label{subsec:caching_robustness_measures}

% Estimating a new pitch transformation on every frame is computationally
% expensive and can also introduce visual jitter when keypoint predictions vary
% slightly between consecutive frames. To reduce this problem, the pipeline
% recomputes the pitch transformation every 15 frames and caches the most recent
% valid transformation between updates.

% This stride-cached design is a compromise between accuracy, stability, and
% runtime. Updating the homography too rarely can make the transformation lag
% behind camera motion, while updating it every frame can amplify keypoint noise.
% A stride of 15 frames provides regular updates while reducing unnecessary
% recomputation.

% Pitch registration remains one of the most important sources of downstream
% error. If the homography is inaccurate, then all pitch-space outputs derived
% from it may be affected, including heatmaps, speed and distance estimates,
% possession proximity, and offside geometry. For this reason, registration
% quality is inspected both visually through bird's-eye outputs and quantitatively
% where keypoint validation metrics are available.

% Once detections have been tracked, assigned team labels, and transformed into
% pitch coordinates, the system generates tactical outputs from the resulting
% structured representation. These outputs are intended to make the broadcast
% video more analytically useful by converting low-level detections into visual
% summaries, player statistics, team possession estimates, pass events, and
% candidate offside situations.

% \subsection{Bird's-eye Visualisation}
% \label{subsec:birdeye_visualisation}

% The bird's-eye visualisation represents the detected players, goalkeepers,
% referees, and ball on a canonical top-down pitch. For each frame with a valid
% pitch transformation, the image-space object positions are projected into pitch
% coordinates and rendered on the pitch model. Players are coloured according to
% their inferred team labels, referees are shown as a separate non-team class,
% and the ball is rendered using its filtered pitch-space position when
% available.

% This visualisation provides an interpretable way to inspect whether the
% detection, team assignment, and pitch registration stages are behaving
% coherently. It is also used to generate side-by-side videos, where the original
% broadcast frame and the corresponding pitch-space representation are displayed
% together. This makes it easier to identify errors such as incorrect team
% labels, unstable homographies, or ball locations that do not match the
% broadcast footage.

% \subsection{Heatmaps, Speed and Distance}
% \label{subsec:heatmaps_speed_distance}

% Player heatmaps are generated by accumulating each tracked player's pitch-space
% positions over time. The pitch is divided into a fixed grid of
% \(480 \times 280\) cells, and each valid player position contributes to the
% corresponding grid location. Heatmaps are generated only when at least 40 valid
% samples are available for a track, reducing the likelihood of producing
% misleading visualisations from short or fragmented tracks.

% To improve readability, the accumulated heatmap is smoothed using a Gaussian
% blur with kernel size 31 and a gamma correction of 0.22. The final heatmap is
% saved both as an image and as a raw numerical array, so that the visual output
% can be inspected while the underlying positional distribution remains
% available for further analysis.

% Speed and distance estimates are computed from changes in player pitch-space
% position over time. Consecutive valid positions for each track are used to
% estimate displacement, which is accumulated to produce total distance
% travelled. Speed is derived from displacement and frame timing. Since small
% errors in pitch registration can produce unrealistically large apparent jumps,
% the system applies a maximum-speed gate of 40 km/h. Movements above this
% threshold are treated as noise and excluded from the accumulated statistics.

% \subsection{Possession and Pass Detection}
% \label{subsec:possession_pass_detection}

% Possession is estimated using the pitch-space distance between the filtered
% ball position and nearby players. For each frame, the system identifies the
% player closest to the ball. A player is considered a possession candidate only
% if the distance to the ball is below 350 cm. To reduce noise from brief
% misdetections or transient ball movements, possession must be stable for at
% least three consecutive frames before being confirmed.

% Team possession is then obtained from the confirmed player's team label. If no
% player satisfies the proximity condition, the frame is treated as having no new
% confirmed possession event. This conservative design reduces the risk of
% assigning possession during periods when the ball is airborne, occluded, or
% incorrectly detected.

% Pass events are detected from stable changes in possession. A pass is recorded
% when confirmed possession changes from one player to another in a temporally
% stable way. This rule-based definition is intentionally simple: it is designed
% to identify likely possession transfers rather than to provide a complete
% semantic classification of football actions. As a result, the pass output is
% best interpreted as a set of candidate pass events that require evaluation
% against manually inspected clips.

% \subsection{Offside Candidate Detection}
% \label{subsec:offside_candidate_detection}

% Offside candidate detection is performed in pitch space using the detected
% players, inferred team labels, ball position, and estimated attacking
% direction. The attacking direction is inferred automatically from accumulated
% team \(x\)-centroids once at least 30 valid team-position samples are
% available, rather than being manually specified for each video.

% For each frame with sufficient information, the system estimates the offside
% line from the second-last defender's pitch-space position. If only one defender
% is available, a fallback line is computed using the available defensive player,
% although this case is less reliable. An attacker is treated as a candidate
% offside player if they are beyond the defensive line by more than a 30 cm
% margin at the relevant moment and are spatially close enough to the ball event
% context to be considered involved in play.

% The output of this module is not intended to replicate full official offside
% judgement. The official law depends on contextual factors such as the exact
% moment the ball is played, active involvement, deliberate play by defenders,
% and body-part eligibility. The system instead detects candidate offside
% situations under simplified geometric assumptions. Candidate events are saved
% as structured JSON records and visualised using an overlay for a fixed display
% duration of 50 frames, allowing them to be inspected during evaluation.

\section{System Overview}
\label{sec:methodology_overview}

The pipeline ingests a broadcast football video and emits four output classes:
an annotated MP4 with bounding boxes, team labels, track identifiers, and
offside indicators; a bird's-eye-view MP4 in pitch-space coordinates; per-track
heatmap PNGs; and JSON logs of pass and offside events together with per-player
match statistics. Internally, processing decomposes into three parallel branches
that converge at a shared pitch-space representation, illustrated in
Figure~\ref{fig:pipeline_overview}.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\linewidth]{images/pipeline_overview.png}
    \caption{Pipeline architecture. Three parallel branches process each frame:
    a generic object detector with multi-object tracker producing per-frame
    player and referee detections that are then assigned to teams (left); a
    dedicated ball detector with a temporal coherence filter (centre); and a
    pitch keypoint detector whose outputs are used to estimate a per-frame
    homography by Direct Linear Transform (right). The three branches converge
    at a shared pitch-space representation, on which all spatial analytics ---
    heatmaps, speed and distance, possession, passes, and offside --- are
    computed.}
    \label{fig:pipeline_overview}
\end{figure}

Three design decisions distinguish this architecture from a single-detector
baseline. First, the ball-class outputs of the generic detector are discarded
in favour of a dedicated single-class ball model, motivated by the per-class
imbalance and small-object difficulty quantified in
Section~\ref{sec:methodology_detection}. Second, goalkeeper team identity is
resolved by a spatial heuristic rather than by the unsupervised clusterer,
because goalkeeper kits are required by competition rules to be visually
distinct from both outfield kits, and a two-cluster model therefore cannot
place them reliably (Section~\ref{sec:methodology_team}). Third, pitch keypoint
inference is the slowest stage of the pipeline; it is run only every fifteen
frames and the resulting homography is cached, exploiting the slow camera
motion characteristic of broadcast football
(Section~\ref{sec:methodology_pitch}).

player's bottom-centre image-space anchor and the ball's position are mapped
through the cached homography in line with the ground-plane validity argument
of Section~\ref{subsec:background_player_projection}. All downstream
analytics operate on these pitch-space positions and are detailed in
Section~\ref{sec:methodology_tactical}.

the unsupervised SigLIP--UMAP--KMeans clustering of
Section~\ref{subsec:team_id_kmeans} on player crops sampled from the first
twenty seconds of footage. Warmup is conceptually outside the per-frame loop

project objective of Section~\ref{sec:aims}.

\section{Development Methodology}
\label{sec:development_methodology}

The project followed a modular, iterative, component-wise development approach.
Each processing stage in Figure~\ref{fig:pipeline_overview} was first
implemented and inspected in isolation, with explicit input and output
contracts as recorded in Table~\ref{tab:pipeline_representations}, before being
integrated into the end-to-end loop. This was a deliberate choice driven by
error propagation: tactical outputs depend on the cumulative correctness of
detection, tracking, team assignment, and pitch registration, so an
under-tested component would fail in ways that surface only at the analytics
stage and would be difficult to attribute to its true source. Component
isolation kept the failure surface small at each stage of development. End-to-end
integration was performed only after each module had been independently verified.

Design decisions for each component were informed first by the literature
reviewed in Chapter~\ref{ch:background} and then checked empirically on a small
set of held-out development clips. The architecture-level choices --- the
two-detector split, the spatial goalkeeper resolver, the cached homography ---
were arrived at through this loop: the literature established the available
techniques and their known failure modes
(Sections~\ref{sec:background_object_detection},
\ref{sec:background_team_id}, and \ref{sec:background_homography}), and
inspection of intermediate outputs on development footage exposed the
specific failure modes that motivated each design departure. The empirical
justifications appearing throughout this chapter (most prominently the
per-class detection breakdown of Section~\ref{sec:methodology_detection}) are
the diagnostic evidence collected during this development loop, separate from
the final quantitative evaluation reported in Chapter~\ref{ch:evaluation}.

Parameters governing component integration --- temporal windows for
smoothing, confidence thresholds for filtering, displacement gates for
plausibility checks --- were calibrated on the same development clips, with
the goal of suppressing transient errors without rejecting plausible
behaviour. They were not selected by formal hyperparameter search: the
project's contribution is in the surrounding architecture and the
component-level design decisions, not in fine-grained parameter tuning.
Where a parameter is principled (for example, a sprinter-ceiling speed cap or
a frame-rate-derived smoothing window) the rationale is stated alongside the
value in the section that introduces it. Implementation-level testing performed
during this development process is documented in
Section~\ref{sec:methodology_testing}.

\section{Object and Ball Detection}
\label{sec:methodology_detection}

The pipeline uses two distinct YOLO detectors. A four-class \emph{generic
detector} locates players, goalkeepers, referees, and the ball, and a
single-class \emph{dedicated ball detector} re-runs ball localisation on every
frame. Only the player, goalkeeper, and referee predictions of the generic
detector flow into the rest of the pipeline; its ball-class outputs are
discarded for the empirical reason developed below. This section covers both
models, addressing FR1 and the first project objective of
Section~\ref{sec:aims}.

\subsection{Generic Four-Class Detector}
\label{subsec:methodology_main_detector}

The generic detector is a YOLOv8m model~\cite{Jocher2023} fine-tuned on the
\textit{Football\_object\_detection\_dataset} (Roboflow), comprising 768
broadcast frames split 618/75/75 across train/validation/test. The dataset
contains 18{,}838 instances across the four classes, distributed unevenly:
players account for 15{,}297 instances --- 12.6 times as many as the ball
class (1{,}213) and 26.3 times as many as the goalkeeper class (581). This
imbalance has direct consequences for per-class performance.

The medium variant (\texttt{yolov8m.pt}) was selected as a compromise between
detection accuracy and inference cost. The pipeline is intended to run on
commodity hardware without a discrete GPU, so a larger backbone would dominate
end-to-end runtime even though it might add a small amount of accuracy. Inputs
were resized to $1280 \times 1280$ to preserve the small-object detail
required for ball localisation, which constrained training-time batch size to
4 on the available NVIDIA A100 GPU. The model was trained for 50 epochs using
Ultralytics 8.4.21 on PyTorch 2.8.0 with the framework's default augmentation
regime; the full run completed in approximately 15 minutes. Complete
training-time hyperparameters are catalogued in
Section~\ref{subsec:methodology_reproducibility}.

Held-out test mAP@50 reached 0.855 on this detector, clearing the threshold
of 0.80 set as success criterion~(i) in Section~\ref{sec:aims}; full per-class
metrics are reported in Chapter~\ref{ch:evaluation}. One per-class result is
relevant here as design evidence: the Player, Goalkeeper, and Referee classes
all reach mAP@50 above 0.98 on the test set, but the Ball class achieves only
0.459 with recall 0.393. Inspection of the normalised confusion matrix during
development showed that 31\% of true balls are classified as background and
40\% of predictions assigned to the Ball class are background false positives.
This pattern --- high precision on the three large-object classes paired with
a recall collapse on the ball --- is the diagnostic evidence that motivated a
separate ball detector.

\subsection{Dedicated Ball Detector}
\label{subsec:methodology_ball_detector}

Two structural factors drive the recall collapse. First, class imbalance: the
ball appears once per image on average while players appear roughly twenty
times, so localisation loss on player boxes dominates the gradient signal.
Second, scale: at broadcast distance the ball occupies only a handful of
pixels, far smaller than the typical anchor distribution of single-stage
detectors~\cite{Redmon2016, redmon2018yolov3}. A single-class detector trained
on a ball-curated dataset removes the first issue entirely and lets model
capacity focus on the second.

The dedicated detector is a YOLOv8x model trained on the
\textit{ball\_dataset} (Roboflow), comprising 1{,}165 frames split 932/114/119
each with exactly one ball annotation. The xlarge variant was chosen because
the marginal inference cost is acceptable for a single-class head and a
larger backbone typically helps on fine-grained small-object features.
Training used the same $1280 \times 1280$ resolution and augmentation regime
as the generic detector, ran for 150 epochs at batch size 8, and completed in
approximately 110 minutes. The resulting model achieves test mAP@50 of 0.950
and recall 0.896 --- a 49 percentage-point absolute improvement over the
generic detector's ball performance, and the headline diagnostic of
Table~\ref{tab:detection_ball_comparison}.

The dedicated detector is run at inference with a deliberately permissive
confidence threshold (\texttt{conf}=0.05) so that low-confidence but
legitimate ball detections survive into the temporal filtering stage. The
filter then selects, from the surviving candidates per frame, the detection
nearest to the previous frame's ball centre subject to a maximum displacement of
80~pixels and a minimum confidence of 0.25. The 80-pixel gate is a
plausibility constraint on per-frame ball motion at typical broadcast frame
rates and resolutions; the 0.25 minimum is the second stage of confidence
gating that the permissive detector threshold defers to. The filter relies on
the dedicated detector producing a high-recall set of candidates per frame, a
behaviour the generic detector cannot reliably provide.

The generic detector runs at inference with confidence threshold 0.2 and IoU
threshold 0.5 for non-maximum suppression, the latter following
Equation~\ref{eq:iou} and the procedure of
Section~\ref{subsec:background_iou_nms}. The 0.2 confidence threshold is
deliberately low: the downstream tracker performs additional quality gating
during association, and recovering a marginal player detection that the
tracker can stabilise across frames is preferable to dropping it at the
detector stage.

\section{Multi-Object Tracking}
\label{sec:methodology_tracking}

The detector outputs of Section~\ref{sec:methodology_detection} are stateless,
but every downstream tactical output depends on stable identities across
frames. The pipeline meets this need with a multi-object tracker, addressing
FR2 and the second project objective of Section~\ref{sec:aims}.

The tracker follows the tracking-by-detection paradigm of
Section~\ref{subsec:background_tracking_by_detection}: per-frame detections
are associated with active tracks by solving a bipartite assignment problem
on a cost matrix derived from spatial overlap between predicted and observed
boxes. The pipeline invokes this through Ultralytics's unified
\texttt{model.track()} interface, which wraps the detector call and applies
the configured association algorithm in-place. The default tracker is
ByteTrack~\cite{ByteTrack}, with BoT-SORT~\cite{BoTSORT} available as a
drop-in alternative through a configuration flag (\texttt{--tracker
bytetrack.yaml} or \texttt{botsort.yaml}). The two algorithms differ in their
association strategies (Sections~\ref{subsec:background_bytetrack}
and~\ref{subsec:background_botsort}); supporting both lets
Chapter~\ref{ch:evaluation} compare them like-for-like against success
criterion~(ii), HOTA $\geq 0.45$.

Both trackers run with their Ultralytics-shipped configuration files
unmodified, in line with the development methodology of
Section~\ref{sec:development_methodology}: tracker-internal hyperparameters
are well-studied~\cite{ByteTrack, BoTSORT} and tuning them was deliberately
out of scope. Holding the configurations to their published defaults also
makes the comparative evaluation a fair baseline rather than a hyperparameter
sweep.

The tracker emits, per frame, a set of identified detections each carrying a
class label, bounding box, confidence score, and stable track identifier. The
per-frame loop splits these by class: player and goalkeeper tracks feed the
team classifier of Section~\ref{sec:methodology_team}, while referee tracks
bypass it because referees belong to neither team and are excluded from
possession reasoning. The ball is handled outside the multi-object tracker
because at most one ball is on the pitch at any moment; the temporal coherence
filter of Section~\ref{sec:methodology_detection} provides the equivalent
single-target stabilisation.

\section{Team Classification}
\label{sec:methodology_team}

Producing per-player team labels without manual annotation directly addresses
the third project objective in Section~\ref{sec:aims} and FR3 of
Table~\ref{tab:methodology_requirements}. The classification problem is
genuinely unsupervised: each match brings a novel pair of kits, no labelled
training data is available, and the only signal is visual appearance. The
pipeline addresses this with the SigLIP--UMAP--KMeans formulation introduced
in Section~\ref{sec:background_team_id}, integrated through the open-source
\texttt{sports} library~\cite{roboflow_sports}, which provides a reference
implementation of the embedding extraction, dimensionality reduction, and
clustering steps. The contribution of this work lies in the surrounding
architecture that makes those building blocks usable inside a per-frame
pipeline: a one-shot warmup phase, a torso-focused cropping strategy,
track-level temporal smoothing, and a separate goalkeeper resolver. Each is
described in turn below.

\subsection{Warmup-Phase Integration}
\label{subsec:methodology_warmup}

The clustering algorithm of Equation~\ref{eq:kmeans_objective} is fitted once
per video, in a dedicated warmup phase that runs before the per-frame loop
begins. The warmup samples frames at a fixed stride
(\texttt{warmup\_stride}=30, roughly one frame per second at 30\,fps) over the
first \texttt{warmup\_seconds}=20 of footage. For each sampled frame the
generic detector of Section~\ref{sec:methodology_detection} is run, only
player-class detections are retained, boxes smaller than $35 \times 35$ pixels
are dropped to exclude unreliably tiny crops, and the surviving boxes are torso-cropped
(Section~\ref{subsec:methodology_torso_crop}). The collected crops are capped
at \texttt{max\_warmup\_crops}=800 and passed in a single batch to
\texttt{TeamClassifier.fit()}, which extracts SigLIP embeddings, projects
them through UMAP, and fits a $k=2$ KMeans model.

The decision to fit once rather than incrementally is the methodological core
of this design. KMeans is sensitive to the empirical distribution of points
seen during fitting, and incremental or per-frame refitting would produce a
moving cluster boundary --- a player whose embedding sat fractionally on one
side of the boundary in frame $t$ could be reassigned in frame $t+1$ purely
because the boundary moved, not because the player's appearance changed.
Fitting once on a representative twenty-second window stabilises the boundary
for the rest of the video. The trade-off is that the system cannot adapt to
sudden visual changes such as a substitute appearing in a markedly different
kit, but in broadcast football this is benign: kits do not change mid-match,
and twenty seconds is sufficient for both teams to appear under typical
broadcast direction. The 800-crop cap is an empirical compromise between fit
stability and the embedding-extraction latency that dominates warmup time.

\subsection{Torso Cropping}
\label{subsec:methodology_torso_crop}

The crops fed into the embedding model are the upper-body subregions of each
player's bounding box, taken between vertical fractions
\texttt{torso\_top}=0.15 and \texttt{torso\_bottom}=0.65. The motivation is
signal-to-noise: the discriminative information for team identity is
concentrated in the torso, where the jersey colour, sponsor logo, and crest
appear, while the lower body contributes shorts (frequently a colour shared
between home and away kits) and grass that varies systematically with the
camera angle rather than with team membership. Excluding the top fraction
removes the head and a thin halo of background; excluding the bottom
fraction removes the lower-body noise just described. Restricting the crop to
this band gives the SigLIP encoder a more homogeneous input distribution and
reduces the risk of the embedding model learning spurious lower-body or
background features as cluster cues.

\subsection{Track-Level Temporal Smoothing}
\label{subsec:methodology_team_smoothing}

Per-frame team predictions are noisy. Even with a well-conditioned cluster
fit and clean torso crops, individual frames can produce wrong assignments due to
motion blur, partial occlusion, an unusual pose, or a player turning their
back to the camera in a way that hides the jersey. Yet team identity is a
constant property of a track --- a player does not change teams during a
match. The \texttt{TrackMajorityVote} class in \texttt{assigner.py} exploits
this by maintaining, for each track identifier, a deque of the last
\texttt{team\_smooth}=30 per-frame predictions and emitting the modal value
as the smoothed team label.

Thirty frames is approximately one second at 30\,fps. This window is short
enough that the smoother reacts quickly when a track identifier is replaced
(when the underlying tracker drops a track and a new identifier takes over),
but long enough that transient per-frame errors are out-voted by the
surrounding correct predictions. The smoothing is applied at the track level
rather than per detection, so detections that arrive without a track
identifier fall back to the raw per-frame prediction.

\subsection{Goalkeeper Resolution}
\label{subsec:methodology_gk_resolver}

The KMeans model is fitted with $k=2$ because there are two outfield teams.
Goalkeeper kits are required by competition rules to be visually distinct
from both outfield kits and from each other, so neither of the two fitted
clusters reliably corresponds to a goalkeeper, and a goalkeeper's embedding
can fall on either side of the cluster boundary essentially by chance. A
$k=3$ fit was considered but rejected: each match contains only two
goalkeepers, the warmup window typically captures few goalkeeper crops, and
$k=3$ on a heavily two-team-dominated crop set is poorly conditioned.

The pipeline resolves goalkeeper identity through a separate spatial
heuristic implemented in \texttt{gk\_resolver.py}. For each frame, the
bottom-centre image-space coordinate of every outfield player on team~0 is
averaged to give a team-0 centroid, and likewise for team~1. Each detected
goalkeeper is then assigned to whichever centroid lies nearer in the image
plane. The reasoning is positional: goalkeepers spend the overwhelming
majority of match time near or behind their own team's most defensive
outfield players. Importantly, this heuristic operates in image-space rather
than pitch-space, which means it continues to work during frames where the
homography of Section~\ref{sec:methodology_pitch} cannot be updated due to
insufficient confident keypoints. The trade-off relies on the implicit assumption 
that the two teams' centroids project to distinguishable image-space locations, 
which is valid for the side-on tactical-camera angles that dominate football broadcasts.

Whether the assembled team-classification stack meets success criterion~(iii)
of Section~\ref{sec:aims} (F1 $\geq 0.85$) is reported in
Chapter~\ref{ch:evaluation}.

\section{Pitch Registration}
\label{sec:methodology_pitch}

Pitch registration is the geometric stage that maps image-space detections
into pitch coordinates, providing the substrate on which all tactical analytics
operate. The pipeline addresses this in two parts: a YOLO-pose model trained
to localise a fixed set of pitch landmarks, and a homography estimator that
consumes those landmarks via the Direct Linear Transform of
Section~\ref{subsec:background_dlt}. This section addresses FR4 and the fourth
project objective of Section~\ref{sec:aims}.

\subsection{Keypoint Detector}
\label{subsec:methodology_keypoint_model}

A YOLOv8x-pose model~\cite{Jocher2023} is fine-tuned to detect a single class
(\emph{pitch}) annotated with 32 keypoints corresponding to geometrically
distinctive features formed by pitch markings: line intersections,
penalty-area and six-yard-box corners, halfway-line endpoints, and tangencies
of the centre circle and penalty arcs. The choice of landmark set follows the
broadcast-football registration literature~\cite{Theiner2022, TVCalib2023};
each keypoint has a known position in pitch coordinates, so any subset
detected with sufficient confidence yields image-to-pitch correspondences
directly usable in DLT.

The detector was trained on the \textit{football\_field\_detection\_dataset}
(Roboflow), comprising 317 broadcast frames split 255/34/28 across train/validation/test, using the same
A100 hardware and Ultralytics 8.4.21 stack as the detection models of
Section~\ref{sec:methodology_detection}. Training-time hyperparameters are
catalogued in Section~\ref{subsec:methodology_reproducibility}, but one
non-default choice is methodologically substantive enough to surface here:
the mosaic augmentation that ships with the YOLO defaults was disabled
(\texttt{mosaic}=0.0). Mosaic concatenates four training images into a single
synthetic input, which is well-motivated for general object detection because
it exposes the model to varied object scales and contexts, but the
augmentation fragments the global geometric structure of a pitch into four
disjoint quadrants. Since the discriminative signal for pitch-keypoint
localisation is precisely the spatial relationships between landmarks --- a
corner flag is identifiable in part because of its position relative to the
goal line and the touchline --- fragmenting that structure trains the model on
inputs whose geometry will never appear at inference. Disabling mosaic was
therefore a deliberate departure from defaults motivated by the structural
mismatch between the augmentation and the fixed-landmark task.

The trained model achieves test detection mAP@50 of 0.995 (the pitch is, in
practice, always present in broadcast frames) and test pose mAP@50 of 0.995
with mAP@50--95 of 0.953. Per-keypoint mean errors cluster around four pixels
on the test set, approximately 0.4\% of the image diagonal. One keypoint
(\texttt{kp\_16}) is an outlier at 18.2 pixels, roughly four times the
median; this is reported here for transparency and discussed alongside its
downstream effect on homography stability in Chapter~\ref{ch:evaluation}.

\subsection{Stride-Cached Homography Estimation}
\label{subsec:methodology_homography}

Pitch keypoint inference is the slowest stage of the pipeline by a substantial
margin: a separate forward pass through a large pose model, served via a
remote inference endpoint. Running it every frame would dominate end-to-end
latency. Two observations make this unnecessary. First, broadcast camera
motion is slow relative to frame rate --- a tactical camera pans over hundreds
of milliseconds, not single-frame intervals. Second, the homography itself,
once estimated from a stable set of keypoints, is robust to small camera
movements. The pipeline exploits this by running keypoint inference only
every \texttt{pitch\_stride}=15 frames, caching the resulting
\texttt{ViewTransformer}, and reusing it for the intervening frames. At
30\,fps that recomputes the homography twice per second, well above the rate
of meaningful camera motion in broadcast football.

When inference does run, three thresholds gate the construction of a new
homography. Each predicted keypoint must clear a per-keypoint confidence
threshold of \texttt{kp\_conf}=0.5; the resulting set of confident keypoints
must contain at least \texttt{min\_good\_kps}=6 entries; and the inference
itself runs with a model-level confidence floor of 0.3. The 6-keypoint
minimum is the most consequential of the three. The DLT system in
Equation~\ref{eq:dlt_system} requires four non-collinear correspondences for
a unique homography, and six provides redundancy that the least-squares
solve uses to suppress per-keypoint localisation noise without becoming
numerically fragile. If insufficient confident keypoints are present in an
inference frame, the previous homography is retained rather than replaced ---
the camera has not moved significantly in the intervening half-second, so the
cached transform remains a reasonable approximation.

The resulting \texttt{ViewTransformer} exposes a vectorised
\texttt{transform\_points} method that maps any image-space coordinate into
pitch-space, applying the projective transformation of
Equation~\ref{eq:homography_mapping} followed by the dehomogenisation of
Equation~\ref{eq:homography_dehomogenised}. Player anchors and the ball are
projected through this method on every frame, supplying the pitch-space
coordinates that Section~\ref{sec:methodology_tactical} consumes. Whether the
resulting projections support the qualitatively coherent tactical outputs
required by success criterion~(iv) is reported in
Chapter~\ref{ch:evaluation}.

\section{Tactical Reasoning}
\label{sec:methodology_tactical}

The four preceding sections supply, on every frame, a set of tracked players
with team labels and confident pitch-space correspondences. Tactical reasoning
is the stage at which these intermediates become the analytical outputs that
motivate the project: bird's-eye trajectories, heatmaps, speed and distance,
possession assignments, pass events, and offside flags. All modules in this
section operate in pitch-space coordinates, in line with the ground-plane
validity argument of Section~\ref{subsec:background_player_projection}, and
are presented in the order in which they consume each other's outputs. The
section addresses FR5 and the fifth project objective of
Section~\ref{sec:aims}.

\subsection{Pitch-Space Projection}
\label{subsec:methodology_projection}

For each tracked player, the bottom-centre of the bounding box is taken as
the ground-plane anchor and projected through the cached homography using
the \texttt{ViewTransformer} of Section~\ref{sec:methodology_pitch}, following
Equation~\ref{eq:player_projection}. The bottom-centre choice is the standard
broadcast-analytics convention: it approximates the point where the player's
feet meet the playing surface, which is the unique location on the bounding
box that lies on the ground plane and therefore satisfies the homography's
planar assumption. The ball is projected from its detected centre. All
downstream modules consume these pitch-space coordinates, expressed in
centimetres with the pitch origin at one corner.

\subsection{Possession Tracking}
\label{subsec:methodology_possession}

Possession is assigned by nearest-eligible-player matching, in the
formulation of Equation~\ref{eq:nearest_ball_holder}: for each frame in which
a ball detection is available, the player whose pitch-space anchor lies
closest to the ball is identified, and possession is assigned to that player
provided the distance is at most \texttt{proximity\_cm}=350\,cm. Referees
are excluded from the eligibility set because they should never be in
possession; the team-classification stage of Section~\ref{sec:methodology_team}
provides this filter through its class labels. If no eligible player lies
within the threshold, possession for that frame is left unassigned rather
than attributed to the nearest-but-still-distant player. The 350\,cm threshold
absorbs the combined effect of bounding-box anchor error and homography
projection noise, which together can shift a player's estimated pitch
position by tens of centimetres even when the underlying detection is
correct, while remaining small enough to disambiguate possession in the
typical congested-midfield scene.

\subsection{Pass Detection}
\label{subsec:methodology_passes}

Pass detection sits on top of possession assignment. Per-frame possession
labels are inherently noisy --- a frame in which the ball is in flight
between two players can briefly attribute possession to a third player who
happens to lie near the ball's trajectory, and a frame in which ball
detection fails can break a stable possession run. The pipeline addresses
this with a hold-stability requirement: a player is considered to genuinely
possess the ball only after the per-frame label has named that player for at
least \texttt{min\_hold\_frames}=3 consecutive frames, and a pass is
registered only when stable possession transitions from one player to a
distinct other. Transitions that fail the stability requirement on either
side are discarded as transient noise.

The detection logic is implemented in the \texttt{\_PossessionTracker} class
in \texttt{offside.py}. A transition between two players on the same team is
logged as a \emph{pass}; a transition between players on opposing teams is
logged as an \emph{interception}. Both are written to the JSON event log
with the schema:

\begin{lstlisting}[basicstyle=\small\ttfamily,frame=single,framerule=0.3pt]
{ "frame_idx": int,
  "passer_track_id": int,
  "passer_team_id": int,
  "ball_pitch_xy": [float, float] }
\end{lstlisting}

\subsection{Offside Detection}
\label{subsec:methodology_offside}

Offside detection extends the pass-detection module with the geometric
criterion of Equation~\ref{eq:offside_basic}. The pipeline implements
\emph{positional} offside only --- the spatial component of Law~11 --- and
does not attempt to resolve the active-involvement clause, which depends on
behavioural cues that broadcast video alone does not reliably expose.

Two pieces of context are required: the attacking direction of each team and
the location of the second-last defender at the moment a pass is initiated.
The attacking direction is recovered automatically by
\texttt{\_AttackDirectionEstimator}, which accumulates pitch-space
$x$-coordinates of each team over the first
\texttt{direction\_min\_samples}=30 sampled frames and assigns the team with
the lower mean $x$ as attacking right (and vice versa). The estimator runs once during the
early phase of the video and the result is fixed thereafter; mid-half
direction switches are out of scope and are recorded as a known limitation in
Section~\ref{sec:methodology_failure_handling}. When the pass-detection
module fires, the offside checker locates the second-last defender of the defending 
team along the attacking $x$-axis and flags the receiver as offside
if their pitch-space $x$-coordinate is beyond the defender's by more than
\texttt{offside\_margin\_cm}=30\,cm. The margin absorbs combined
detection-and-projection noise, preventing flags on plays where a player
appears fractionally beyond the defender purely because of pixel-level
anchor error compounded by homography uncertainty.

Offside events trigger a visual annotation that persists for
\texttt{display\_frames}=50 frames (approximately 1.7\,s at 30\,fps): the
offending player's box is drawn red on the broadcast frame, marked red on the
bird's-eye view, and a dashed red line is drawn at the offside
$x$-coordinate to indicate the defender's line.
Each event is logged with the schema:

\begin{lstlisting}[basicstyle=\small\ttfamily,frame=single,framerule=0.3pt]
{ "frame_idx": int,
  "pass_event": { ... pass-event fields above ... },
  "offside_line_x": float,
  "offside_players": [
    { "track_id": int, "pitch_xy": [float, float] }, ...
  ] }
\end{lstlisting}

\subsection{Speed and Distance}
\label{subsec:methodology_speed}

Per-track speed and cumulative distance are computed by finite-differencing
the pitch-space anchor across consecutive frames, following the velocity
formulation of Equation~\ref{eq:velocity_pitch_space} and the distance
accumulation of Equation~\ref{eq:distance_pitch_space}. Speed is reported in
km/h and distance in metres in the per-player block of the stats JSON
(\texttt{distance\_m}, \texttt{avg\_speed\_kmh}, \texttt{max\_speed\_kmh}). A
plausibility cap (\texttt{max\_speed\_kmh}=40) rejects per-frame
displacements implying speeds beyond this threshold: elite sprinters peak
around 35--37\,km/h, so 40\,km/h leaves headroom above the realistic ceiling
while still flagging single-frame jumps from tracking and projection noise.
Frames whose finite-differenced speed exceeds the cap have their
displacement contribution zeroed for that frame, preserving the cumulative
distance estimate against single-frame noise spikes at the cost of also
rejecting genuine high-speed motion above 40\,km/h --- a regime that
essentially does not occur in football.

\subsection{Heatmaps}
\label{subsec:methodology_heatmaps}

Per-track positional heatmaps are accumulated on a pitch-space grid,
following the histogram construction of Equation~\ref{eq:heatmap_histogram}.
The grid defaults to $480 \times 280$ bins covering the full pitch, giving a
spatial resolution of roughly $20 \times 25$\,cm per bin --- finer than the
projection-pipeline noise floor and coarser than per-frame jitter, so each
bin aggregates many frames of presence rather than acting as a noise
multiplier. On each frame the bin containing each player's pitch-space
anchor is incremented. At the end of the video, each track's accumulated
histogram is post-processed: a Gaussian smoothing pass is applied as in
Equation~\ref{eq:heatmap_smoothing}, followed by a $\gamma=0.22$ correction
to compress dynamic range and reveal less-visited regions. The $\gamma$
correction is a display choice rather than a statistical operation: the raw
histogram is also written to disk as an NPY array so that downstream analysis
can operate on the unsmoothed counts.

\section{System Engineering and Reproducibility}
\label{sec:methodology_system}

\subsection{Pipeline Orchestration}
\label{subsec:methodology_orchestration}

The modules described in the preceding sections are integrated through a
single orchestration script (\texttt{run.py}) that exposes the pipeline as a
command-line tool. The implementation follows a modular layout under
\texttt{src/}, with one subpackage per processing stage --- \texttt{ball/},
\texttt{heatmap/}, \texttt{pitch/}, \texttt{stats/}, \texttt{team/}, and
\texttt{pipeline/} --- so that each component can be modified, tested, or
replaced independently. The tracker swap is the cleanest instance of this
modularity: switching between ByteTrack and BoT-SORT requires only a different
configuration filename passed to the Ultralytics tracker interface, with no
changes elsewhere in the codebase, satisfying NFR1 of
Table~\ref{tab:methodology_requirements}.

Execution proceeds in two phases. The warmup phase of
Section~\ref{subsec:methodology_warmup} runs once at the start of each video
to fit the team-classification model on a representative crop set; the
per-frame loop then iterates through the remaining frames in the order shown
in Figure~\ref{fig:pipeline_overview}. The two-phase structure is required by
the cluster-stability argument of Section~\ref{subsec:methodology_warmup} and
provides a natural place to log fitting diagnostics separately from per-frame
output.

Several caching layers amortise computational cost: pitch keypoint inference
is cached every fifteen frames
(Section~\ref{subsec:methodology_homography}); the previous ball position is
held as a one-frame cache for the temporal coherence filter
(Section~\ref{sec:methodology_detection}); per-track team-prediction history
is held in a thirty-frame deque
(Section~\ref{subsec:methodology_team_smoothing}); and per-track heatmap
arrays are accumulated in memory until end-of-video. The heatmap arrays are
the largest cache at $480 \times 280$ floats per active track and remain
modest in absolute terms, so the pipeline runs in a single Python process
without explicit memory management.

\subsection{Output Formats}
\label{subsec:methodology_outputs}

The output format reflects the dual audience for the pipeline's results,
satisfying NFR3. An annotated MP4 and a bird's-eye-view MP4 are produced for
human inspection; per-track heatmap PNGs serve the same purpose. For machine
consumption, the raw heatmap counts are also exported as NPY arrays, and
detected pass and offside events together with per-player match statistics
are serialised to JSON using the schemas of
Section~\ref{sec:methodology_tactical}. The JSON outputs are the inputs that
Chapter~\ref{ch:evaluation} consumes for quantitative assessment of success
criterion~(iv).

Operational ergonomics are handled by a wrapper shell script
(\texttt{run.sh}) that exposes mode presets --- \texttt{preview} for short
test clips, \texttt{full} for end-to-end processing of complete matches, and
\texttt{debug} for verbose intermediate logging --- so that common
invocations do not require remembering the underlying argument set. A
separate Streamlit interface provides a graphical front-end accepting a video
upload and surfacing the same outputs as the command-line entry point,
included as a demonstration that the pipeline can be packaged for use
beyond the development environment.

\subsection{Reproducibility}
\label{subsec:methodology_reproducibility}

Three categories of reproducibility commitment apply to the pipeline,
satisfying NFR2.

\paragraph{Environment.} Training was carried out on an NVIDIA A100-SXM4-80GB
GPU using Python~3.11, Ultralytics~8.4.21, PyTorch~2.8.0, and CUDA~12.8;
inference is intended for and developed against an Apple~M2 Pro (no discrete
GPU). The pipeline runs end-to-end in a single Python process without
multi-GPU coordination, simplifying the inference environment.

\paragraph{Models, datasets, and configuration.} Three YOLO models are
fine-tuned by this project: the four-class generic detector
(Section~\ref{sec:methodology_detection}), the dedicated ball detector
(Section~\ref{sec:methodology_detection}), and the pitch-keypoint detector
(Section~\ref{sec:methodology_pitch}). Each is trained on a publicly
available Roboflow dataset (\textit{Football\_object\_detection\_dataset},
\textit{ball\_dataset}, and \textit{football\_field\_detection\_dataset}
respectively), with hyperparameters as reported in the corresponding sections. Trained weights are
saved locally; the keypoint detector is additionally served via Roboflow's
serverless inference endpoint at runtime. All pipeline-level hyperparameters
discussed throughout this chapter are exposed as command-line arguments by
\texttt{run.py}, with mode-specific defaults in \texttt{run.sh}.

\paragraph{Limitations.} Two aspects of the pipeline cannot be reproduced
bit-exactly: random initialisation in YOLO training was not seeded, so
re-running the training procedure will produce numerically distinct (but
behaviourally equivalent) weights, and the Roboflow-hosted inference endpoint
is a third-party service whose identical availability cannot be guaranteed
into the future. Local deployment of the keypoint model on the trained
weights is supported as a fallback for replicators without the hosted
endpoint.
