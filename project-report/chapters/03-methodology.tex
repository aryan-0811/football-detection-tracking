\section{Chapter Overview}
\label{sec:methodology_overview}

Chapter~\ref{ch:background} surveyed the methods relevant to each stage of a
broadcast football analysis pipeline---object detection, tracking, team
identification, pitch registration, and the derivation of tactical outputs---without
committing to a specific realisation. This chapter moves from that theoretical
grounding to the concrete system developed for this project, describing the
architecture and implementation of each stage and the reasoning behind the
choices made at each one.

The pipeline takes a single broadcast video stream as input and processes it
through a sequence of stages: player, goalkeeper, referee and ball detection with
dedicated YOLO models; multi-object tracking by association; team identification
via SigLIP embeddings of torso crops followed by dimensionality reduction and
clustering; pitch registration from keypoint correspondences resolved into a
planar homography; and projection of tracked players into a pitch-coordinate
frame from which heatmaps, speed and distance, possession, and offside geometry
are derived. Each stage consumes the output of those preceding it, and the
chapter follows this same ordering so that each design decision can be read in
the context of the inputs it must handle and the outputs it must produce.

For each stage, the chapter justifies the design choice against the alternatives
surveyed in Chapter~\ref{ch:background}, specifies parameter values and
algorithmic details in sufficient detail for a peer to reproduce the work, and
presents illustrative outputs from the implemented system. The datasets used
for training the bespoke detection and keypoint models are described, together
with the training procedure and the resulting model artefacts. The chapter also
defines the evaluation methodology that will be applied in
Chapter~\ref{ch:evaluation}, setting out the metrics, test data, and protocols
by which each pipeline stage and the system as a whole will be assessed.

Chapter~\ref{ch:results} presents the results obtained by running the pipeline
on evaluation data, and Chapter~\ref{ch:evaluation} discusses those results and
their implications; the present chapter is concerned with how the system was
built and why, not with its measured performance.

\section{Requirements and Design Objectives}
\label{sec:methodology_requirements}

Before the system architecture is presented, this section sets out the
requirements the pipeline is designed to meet. Functional requirements define
what the system must do; non-functional requirements define the qualities it
should exhibit; and success criteria state the measurable thresholds against
which each component will be judged in Chapter~\ref{ch:evaluation}. The
requirements derive from the project aims set out in
Chapter~\ref{ch:introduction} and are framed here in terms suited to system
design, so that the architectural and implementation choices described in the
remainder of this chapter can be read against them.

\subsection{Functional Requirements}
\label{subsec:functional_requirements}

The functional requirements describe the end-to-end behaviour of the pipeline.
The system takes as input a single broadcast football video and produces, for
each frame, a set of per-object detections, persistent track identities, team
labels, pitch-coordinate positions, and a collection of derived tactical
outputs. The requirements are decomposed by pipeline stage so that each
subsequent section of this chapter can be mapped directly to the requirement
it satisfies.

\paragraph{FR1: Object detection.} The system shall detect the four classes
relevant to broadcast football analysis---players, goalkeepers, referees, and
the ball---in each frame of the input video, returning axis-aligned bounding
boxes and class labels. Given the extreme scale disparity between outfield
players and the ball, detection of the ball shall be handled by a dedicated
model operating at the same input resolution but with its own training regime
and confidence regime, rather than relying on the generic detector alone.

\paragraph{FR2: Multi-object tracking.} The system shall maintain consistent
identities for detected players, goalkeepers, and referees across frames,
associating detections over time into persistent tracks. Tracker choice shall
be configurable so that alternative association strategies can be compared.
Ball identity is not required to persist, since the ball is a single object
and its per-frame localisation is sufficient for downstream use.

\paragraph{FR3: Team identification.} The system shall assign each tracked
player to one of two teams without manual labels, using visual appearance
alone. The assignment shall be stable over time: transient misclassification
on a single frame shall not be allowed to propagate as the team label returned
for a track. Goalkeepers, whose kits typically differ from their outfield
teammates, shall be resolved to a team by a separate mechanism rather than
being forced into the outfield clustering.

\paragraph{FR4: Pitch registration.} The system shall recover the planar
homography between the broadcast image and a canonical pitch model, permitting
image-plane coordinates to be mapped to pitch-plane coordinates. Registration
shall tolerate the fact that the full pitch is rarely visible in a broadcast
frame, and shall degrade gracefully when insufficient correspondences are
available in a given frame by reusing the most recent valid transform until a
new valid estimate is obtained.

\paragraph{FR5: Tactical output generation.} From the projected per-track
trajectories the system shall derive a set of tactical outputs: per-player
heatmaps of pitch occupation, speed and distance statistics, team possession,
pass events, and offside candidate frames. Each output shall be produced in
pitch coordinates, so that the reported quantities are physically meaningful
rather than tied to the broadcast view.

\paragraph{FR6: Visualisation and persistence.} The system shall render the
principal outputs for inspection---annotated broadcast video with detection,
track, and team overlays; a bird's-eye projection of tracked objects onto the
pitch model; and rendered heatmaps---and shall persist these together with any
per-frame numerical outputs so that results can be reviewed offline and used
as input to the evaluation procedure.

\subsection{Non-functional Requirements}
\label{subsec:nonfunctional_requirements}

The non-functional requirements describe qualities the system should exhibit
irrespective of the specific outputs it produces.

\paragraph{NFR1: Reproducibility.} The full configuration required to
reproduce a given run---model weights, parameter values, and preset
selections---shall be recoverable from a single set of launch arguments, and
the training of any bespoke models shall be recorded with sufficient detail
(dataset, hyperparameters, training curves) to be repeated by a peer.

\paragraph{NFR2: Modularity.} Each pipeline stage shall be implemented as a
self-contained component with a clearly defined input and output contract, so
that an individual stage can be replaced, reconfigured, or evaluated in
isolation without requiring changes to the surrounding system.

\paragraph{NFR3: Configurability.} Parameter values that govern behaviour at
runtime---detection thresholds, tracker selection, inference strides, warmup
sizes, smoothing windows, displacement gates---shall be exposed through the
command-line interface rather than embedded in source code, and reasonable
defaults shall be provided in a single location so that the system can be run
without a long argument list.

\paragraph{NFR4: Robustness to broadcast artefacts.} The pipeline operates on
broadcast video rather than instrumented capture, and must therefore tolerate
partial occlusion, motion blur, pan-tilt-zoom camera motion, and the
appearance of on-screen graphics without catastrophic failure. Robustness is
treated as a design objective at each stage rather than as a single global
property, with appropriate mechanisms (temporal smoothing, displacement gates,
majority-vote filtering) introduced where individual stages are known to be
sensitive.

\paragraph{NFR5: Graceful degradation.} When an individual stage cannot
produce a usable output for a given frame, the pipeline shall continue to
operate on subsequent frames rather than terminate. For pitch registration in
particular, the system shall retain the most recent valid homography and
reuse it until a new valid estimate is produced. The extent to which other
stages meet this objective is discussed alongside the relevant component.

\paragraph{NFR6: Inspectability.} Intermediate outputs of the pipeline---raw
detections, tracked identities, projected positions, registration overlays,
per-track statistics---shall be exposable for inspection, so that failure
modes can be localised to specific stages during development and evaluation,
and so that the evaluation procedure can assess each stage independently.

\paragraph{NFR7: Runtime.} The pipeline is intended for offline post-match
analysis rather than real-time or live operation. Runtime is therefore not a
primary design objective: the system shall complete processing of a broadcast
clip on a single consumer GPU within a reasonable working session, but no
throughput target is set, and design decisions throughout the pipeline
prioritise per-stage accuracy and inspectability over end-to-end speed. The
measured processing cost and the stages that dominate it are discussed
alongside the results in Chapter~\ref{ch:evaluation}.

\subsection{Success Criteria}
\label{subsec:success_criteria}

The success criteria restate, in measurable form, the conditions under which
each functional requirement is considered satisfactorily met. Specific
numerical thresholds are stated where they derive from the project aims set
in Chapter~\ref{ch:introduction}; the full evaluation protocols by which
these are assessed are given in Section~\ref{sec:evaluation_methodology} and
applied in Chapter~\ref{ch:evaluation}.

\paragraph{SC1 (FR1, Detection).} The generic object detector shall achieve a
mean average precision of at least \todo{[target mAP@0.5 from Ch1]} on the
held-out test split, with per-class performance reported for player,
goalkeeper, and referee. The dedicated ball detector shall achieve a per-frame
recall of at least \todo{[target]} under the confidence regime used at
inference, at a false-positive rate that the temporal-filtering stage
(Section~\ref{sec:ball_pipeline}) can reasonably suppress.

\paragraph{SC2 (FR2, Tracking).} Tracking performance shall be reported using
the HOTA family of metrics~\cite{HOTA2020}, with a target HOTA of at least
\todo{[target]} on the evaluation clips. Identity switches shall be reported
alongside and kept below \todo{[target]} per minute of broadcast time.

\paragraph{SC3 (FR3, Team identification).} The per-frame team assignment
shall agree with manually annotated ground truth on at least \todo{[target]}
of sampled player crops, and the per-track label returned after temporal
smoothing shall agree on at least \todo{[target]} of tracks. Goalkeeper
assignment shall be correct on at least \todo{[target]} of goalkeeper tracks.

\paragraph{SC4 (FR4, Registration).} Pitch registration shall achieve a mean
reprojection error of no more than \todo{[target, in pitch metres]} on
evaluation frames where ground-truth correspondences are available, and shall
produce a valid homography on at least \todo{[target]} of frames in a
continuous broadcast clip.

\paragraph{SC5 (FR5, Tactical outputs).} Tactical outputs shall be plausible
when inspected against the broadcast source: heatmaps shall reflect known
player roles, speed and distance values shall fall within physically
reasonable ranges reported in the sports-science literature, possession
totals shall be consistent with a human annotator's reading of the clip,
detected pass events shall match annotated passes with a precision and recall
of at least \todo{[target]}, and offside candidate frames shall agree with a
human referee's reading.

\paragraph{SC6 (End-to-end usefulness).} When run end-to-end on unseen
broadcast footage, the system shall produce the full set of visualisations
and statistics described under FR6 without manual intervention, and the
resulting outputs shall be informative enough that a non-specialist viewer
can interpret the match in tactical terms from the produced artefacts alone.

\section{System Architecture}
\label{sec:methodology_architecture}

This section describes the architecture of the pipeline at a level that
permits the work to be reproduced by a peer. The pipeline is presented first
as a structural overview, showing how the stages are composed and where
models, rule-based logic, and caching enter the design
(Section~\ref{subsec:pipeline_overview}). The data objects passed between
stages are then specified with their types, shapes, and provenance
(Section~\ref{subsec:data_flow}), and the user-facing outputs of the system
are catalogued (Section~\ref{subsec:system_outputs}). The algorithmic
content of each stage is deferred to Sections~\ref{sec:detection_tracking}
through~\ref{sec:tactical_outputs}, which describe how the stages are
realised and why.

\subsection{Pipeline Overview}
\label{subsec:pipeline_overview}

Figure~\ref{fig:pipeline_architecture} shows the end-to-end architecture.
A single broadcast video frame is processed through two parallel branches
that converge at a pitch-space projection stage, after which all
higher-level analytics operate in a shared pitch coordinate frame rather
than in the image plane.

\begin{figure}[t]
  \centering
  \includegraphics[width=\linewidth]{images/pipeline_overview.png}
  \caption{End-to-end pipeline architecture. The broadcast frame enters at
  the top and is processed through two parallel branches---appearance-based
  detection and tracking on the left, pitch-geometry recovery on the
  right---which converge at the pitch-space projection stage. All
  higher-level tactical analytics operate in pitch coordinates. Section
  numbers on the left indicate where each stage is described in detail.}
  \label{fig:pipeline_architecture}
\end{figure}

The left branch handles \emph{what} is in the frame: objects are detected,
outfield actors are tracked over time, and each tracked player is assigned
to a team. The right branch handles \emph{where} the frame sits in
pitch-space: canonical landmarks on the pitch are detected and resolved
into a planar homography. The two branches are independent---no stage in
one depends on an output of the other until they converge---and this
independence is exploited at runtime, since pitch keypoints change slowly
relative to player positions and the right branch is therefore executed at
a lower frequency than the left.

\paragraph{Models and rule-based components.} The appearance stages are
fully model-based. A generic YOLO detector is run on each frame and
produces bounding boxes for players, goalkeepers, and referees; a second
YOLO detector dedicated to the ball is run in parallel on the same frame
and is the authoritative source of ball localisation (the ball-class
outputs of the generic detector are discarded, for reasons given in
Section~\ref{sec:detection_tracking}). Pitch landmarks are produced by a
keypoint model. The team identification stage combines a pretrained
vision-language embedding model (SigLIP) with dimensionality reduction
(UMAP) and a small unsupervised clustering step (k-means, $k=2$). The
tracker is a learning-free multi-object association algorithm (ByteTrack,
with BoT-SORT selectable) applied to the generic detector's player,
goalkeeper, and referee outputs only; the ball is never passed to the
tracker and instead passes through a lightweight temporal filter (nearest
neighbour to the previous accepted position under a displacement gate)
described in Section~\ref{sec:detection_tracking}. All stages downstream
of projection---heatmap accumulation, speed and distance computation,
possession, pass detection, offside geometry---are rule-based: they
operate deterministically on projected trajectories and carry no learned
parameters.

\paragraph{Caching and stride.} Two caching mechanisms are used to control
the per-frame computational cost. First, pitch keypoint inference is run
once every \texttt{pitch-stride} frames (default 15) and the resulting
homography is reused on intervening frames; when a new inference fails to
produce a valid estimate, the last valid homography is retained. Second,
team classification is fitted once during a warmup window at the start of
the video (default 20\,s in the production preset) and reused thereafter;
per-track team labels are produced by applying the fitted classifier to
new crops and are stabilised by a majority-vote smoother over a 30-frame
window. No other stage caches state across frames beyond the track state
held internally by the tracker.

\paragraph{Execution model.} The pipeline is driven by a single
orchestration loop in \texttt{src/pipeline/run.py} that reads frames
sequentially, invokes the stages in the order shown in
Figure~\ref{fig:pipeline_architecture}, and writes outputs to disk. The
loop is deliberately sequential rather than concurrent: the stages have
strict data dependencies, intermediate outputs are required for
inspection and evaluation (NFR6), and real-time operation is explicitly
out of scope (NFR7).

\subsection{Data Flow and Intermediate Representations}
\label{subsec:data_flow}

The data objects passed between stages are summarised in
Table~\ref{tab:data_flow}. Where possible the pipeline reuses the
\texttt{supervision} library's native \texttt{Detections} type as the
common currency of the detection--tracking--team-identification branch,
which simplifies interoperation with the off-the-shelf tracker and
annotation utilities. The cost of this choice is that per-stage metadata
that does not fit the \texttt{Detections} schema must be handled out of
band, as described below.

\paragraph{Detection and tracking record.} The core data object in the left
branch is \texttt{supervision.Detections} with four populated fields. A
raw detection set $\mathcal{D}$ of $N$ objects carries $\mathbf{B} \in
\mathbb{R}^{N \times 4}$ for bounding boxes in absolute pixel coordinates
$(x_1, y_1, x_2, y_2)$, $\mathbf{c} \in [0,1]^N$ for per-detection
confidences, and $\mathbf{k} \in \{0,1,2,3\}^N$ for class identifiers
under the detector's label set $\{0\!:\!\mathrm{ball},\,
1\!:\!\mathrm{GK},\, 2\!:\!\mathrm{player},\, 3\!:\!\mathrm{referee}\}$.
The tracker additionally populates $\mathbf{t} \in \mathbb{Z}^N$ with
integer track identifiers on frames where association has succeeded; on
frames where the tracker has produced no identifier, this field is
absent.

\paragraph{Encoding of team membership.} Team membership is encoded by
overwriting the \texttt{class\_id} field in place rather than by adding a
new field to the detection record. Following team assignment, the
semantics of \texttt{class\_id} change: outfield players carry
$\mathrm{class\_id} \in \{0, 1\}$ denoting team A or team B, goalkeepers
are resolved to the same two-valued alphabet where possible and to the
value $2$ otherwise, and referees are forced to $2$. This reinterpretation
is deliberate: downstream renderers and exporters consume the field
uniformly as a palette index, and the reuse avoids maintaining two
parallel arrays that must be kept in lockstep. It is documented here
explicitly because the value $2$ denotes \emph{referee or unresolved
goalkeeper} after team assignment, not \emph{player} as in the raw
detector output.

\paragraph{Ball as a distinct data stream.} The ball is handled as a
separate \texttt{supervision.Detections} instance throughout the pipeline.
It is never merged with the outfield detection set, never carries a
\texttt{tracker\_id}, and is consumed by downstream stages (bird's-eye
render, offside detector, stats tracker) as a parallel argument alongside
the outfield detections. On frames where the temporal filter rejects all
candidates, the ball set is empty; downstream consumers treat this
condition as a missing-ball frame rather than as an error. The rationale
for this parallel-stream design is given in
Section~\ref{sec:detection_tracking}.

\paragraph{Pitch geometry and projected coordinates.} Pitch geometry is
carried on a separate \texttt{ViewTransformer} object rather than attached
to detections. The transformer encapsulates the $3 \times 3$ homography
$H$ from broadcast-image pixels to a canonical pitch plane expressed in
centimetres. Downstream consumers that require pitch-space positions
(heatmap accumulation, speed and distance computation, possession, pass
detection, offside geometry) receive the detection set and the
transformer as separate arguments and compute
$\tilde{\mathbf{p}} = H \cdot [x, y, 1]^\top$ internally from the
bottom-centre anchor of each bounding box, applying the standard
perspective divide. This out-of-band handling mirrors the fact that
geometry changes on a different schedule from appearance: a single
transformer is used across all detections in a frame, and often across
multiple frames under the keypoint-stride caching scheme.

\paragraph{Event records.} Higher-level outputs produced by the analytics
stage (possession segments, pass events, offside candidate frames) are
represented as discrete records of the form $(t, \tau, \mathcal{I})$, where
$t$ is a frame timestamp, $\tau$ is an event type, and $\mathcal{I}$ is a
reference to the tracks and teams involved in the event. Records are
accumulated across the video and exported as structured logs alongside the
rendered visualisations.

\paragraph{Persisted artefacts.} Each run produces a deterministic set of
on-disk artefacts under a timestamped output directory: the annotated
broadcast video, the bird's-eye render (when enabled), the side-by-side
composite (when enabled), per-track heatmap images, per-track movement
summaries, a possession timeline, a pass event log, and a flagged-frames
list for offside candidates. These artefacts together form the input to
the evaluation procedure described in
Section~\ref{sec:evaluation_methodology} and are the basis of the results
reported in Chapter~\ref{ch:evaluation}.

\subsection{System Outputs}
\label{subsec:system_outputs}

The system produces three families of outputs, corresponding to the three
principal ways the results are consumed: inspection of the broadcast
through augmented video, compact summary through bird's-eye
visualisation, and analytical use through numerical exports.

\paragraph{Augmented broadcast.} The annotated broadcast video renders
per-frame detections, persistent track identifiers, and team colour
coding back onto the source frame. This artefact is the most direct
qualitative evidence that the pipeline is operating correctly: detection
misses, identity switches, and team misassignments are immediately
visible against the broadcast action.

\paragraph{Bird's-eye visualisation.} The bird's-eye render projects every
tracked outfield object, along with the ball, onto a scale drawing of the
pitch. Objects are drawn as coloured discs whose colour encodes the
(post-team-assignment) class identifier: two team colours for outfield
players and resolved goalkeepers, a distinct colour for referees and
unresolved goalkeepers, and a neutral colour for the ball. When an
offside candidate has been flagged on a given frame, the offending player
is recoloured and the relevant offside line is overlaid. The render is
stateless: each frame is drawn from the current set of projected
positions alone, without trails or accumulated history, which keeps the
bird's-eye faithful to the instantaneous pitch state. The bird's-eye can
be produced as a standalone video, as a component of a side-by-side
composite with the broadcast, or both simultaneously.

\paragraph{Tactical outputs and numerical exports.} The tactical analytics
produce a set of quantitative outputs intended for post-hoc analysis
rather than inline display. Per-player heatmaps capture occupation
density in pitch space. Per-player movement summaries record distance
covered and speed statistics over the sequence. A possession timeline
records which team is in possession at each moment. Pass events and
offside candidate frames are accumulated as event records. Each output is
persisted in a structured, machine-readable form (CSV or JSON as
appropriate to the shape of the data) so that the evaluation procedure
can compare against ground-truth annotations without re-running the
pipeline, and so that the outputs can be consumed by downstream tools
outside the scope of this project.

\section{Datasets and Model Training}
\label{sec:datasets_training}

Three bespoke models are used in the pipeline: a generic object detector
for outfield actors, a dedicated ball detector, and a pitch keypoint
detector. Each was trained on a Roboflow-hosted dataset of broadcast
football imagery, using the Ultralytics training harness with variants of
the YOLOv8 architecture. This section describes the datasets
(\S\ref{subsec:datasets}) and the training procedure for each model
(\S\ref{subsec:train_generic}, \S\ref{subsec:train_ball},
\S\ref{subsec:train_keypoints}). Results on held-out training splits are
reported alongside the pipeline stage that consumes each model, where
they inform the design discussion directly; full pipeline-level
evaluation appears in Chapter~\ref{ch:evaluation}. A fourth model used by
the pipeline---the SigLIP vision--language encoder consumed by the team
identification stage---is used off-the-shelf without fine-tuning and is
described in Section~\ref{sec:team_identification} rather than here.

\paragraph{Generic detector dataset.} The generic detector was trained on
a Roboflow-hosted dataset of broadcast football frames curated
collaboratively as a shared resource for broadcast football analysis, to
which the author contributed additional annotations of frames sourced
from a publicly available broadcast football dataset hosted on Kaggle.
The resulting dataset contains 768 annotated frames split 618/75/75 for
training, validation, and test, and carries the four classes required by
this work: \emph{ball}, \emph{goalkeeper}, \emph{player}, and
\emph{referee}. The class distribution is heavily imbalanced: the
\emph{player} class accounts for the great majority of annotations,
while goalkeepers, referees, and the ball each appear at most once per
frame and sometimes not at all. This imbalance motivates the use of a
separate, single-class dataset for the ball, described next.

\paragraph{Ball detector dataset.} The dedicated ball detector was trained
on a separate Roboflow-hosted dataset built specifically for small-object
detection of the ball against broadcast backgrounds. It contains 1,165
annotated frames split 932/114/119 for training, validation, and test,
with a single \emph{ball} class; the Ultralytics log records the model's
class head being overridden from 80 to 1 on initialisation. Sourcing a
ball-only dataset rather than extracting ball annotations from the
generic dataset yields a substantially larger pool of positive examples
(932 versus 618 frames) and permits augmentation, input resolution, and
loss weighting to be tuned for a single small-object class without
having to balance against the needs of the outfield classes.

\paragraph{Pitch keypoint dataset.} The pitch keypoint model was trained
on a Roboflow-hosted dataset of broadcast football frames annotated with
32 canonical pitch landmarks together with a pitch bounding box. The
dataset is comparatively small (approximately 290 training frames, 34
validation, 28 test). Two factors make this size acceptable: keypoint
annotation is considerably more labour-intensive than bounding-box
annotation, and the geometric regularity of a football
pitch---fixed markings at fixed distances---means that a relatively
small dataset can cover the space of camera viewpoints encountered in
broadcast footage. The keypoint layout defines a horizontal-flip
symmetry (\texttt{flip\_idx}) so that horizontal augmentation can be
applied without destroying left--right keypoint identities.

\subsection{Generic Object Detector Training}
\label{subsec:train_generic}

The generic detector was initialised from the pretrained
\texttt{yolov8m.pt} checkpoint and fine-tuned for 50 epochs on the
four-class dataset. Training was run on a Tesla~T4 GPU in a Google Colab
environment, at an input resolution of $1280 \times 1280$ to preserve
fine detail on small or distant players, with a batch size of 4
constrained by GPU memory at that resolution. The Ultralytics
\texttt{auto} optimiser selected AdamW with default learning-rate
schedules. Augmentation settings were the Ultralytics defaults for a
detection task (HSV jitter, mosaic, horizontal flip, random erasing, and
RandAugment), with rotation, shear, and perspective augmentation
disabled as inappropriate for a broadcast view with a largely fixed
horizon.

\paragraph{Artefact retention.} The final weights from this run were
deployed to Roboflow for downstream use and retrieved from that
deployment for pipeline inference. The per-epoch \texttt{results.csv}
from the training run was not preserved in the project repository, so
loss and mAP trajectories over training cannot be reconstructed. The
final validation and test summaries emitted at the end of training are
retained in the training notebook and are reported in
\S\ref{sec:detection_tracking}, where they inform the design choice of
treating the ball as a separate detection stream. This is a reproducibility
limitation that the remaining two training runs, reported below, avoid.

\section{Small-Object Detection and Dedicated Ball Detection}
\label{sec:background_ball_detection}
 
Although the ball is the primary object of interest in football, it is also
the hardest to detect reliably in broadcast footage. At typical broadcast
resolution, the ball subtends only a few dozen pixels in diameter, moves
rapidly enough to produce motion blur, and is frequently occluded by players
or absent from the frame entirely~\cite{Gualtieri2023}. These properties
place it firmly in the small-object detection regime, where standard
detectors trained jointly on all classes tend to underperform because larger,
more visually prominent objects dominate the training
signal~\cite{Theiner2022}.
 
 
\subsection{Why Small Objects Are Harder to Detect}
\label{subsec:background_small_object_difficulty}
 
The COCO benchmark defines a small object as one whose bounding box occupies
fewer than $32 \times 32$ pixels~\cite{lin2014microsoft}. By this standard,
the ball in a wide-angle broadcast frame is consistently small, often below
$20 \times 20$ pixels depending on camera zoom.
 
Small-object detection is inherently harder for two reasons. First, the IoU
criterion (Equation~\eqref{eq:iou}) becomes disproportionately sensitive to
localisation error at small scales: a fixed pixel displacement $\delta$
produces a much larger IoU drop on a small box than on a large one. As shown
in Figure~\ref{fig:iou_degradation}, a 2-pixel shift reduces IoU from 1.0 to
0.78 on a $16 \times 16$ box but only to 0.94 on a $64 \times 64$ box. This
makes ball detection acutely sensitive to blur, noise, and detector
uncertainty. Second, in convolutional architectures the spatial resolution of
feature maps decreases with depth; by the deepest layers, small objects may
occupy only a single cell or be lost entirely. The FPN neck described in
Section~\ref{subsec:background_yolo} partially mitigates this, but the
representation of very small objects remains inherently weaker than that of
larger ones~\cite{lin2017feature}.
 
\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.75\linewidth]{images/iou_degradation.png}
    \caption{Effect of pixel displacement $\delta$ on IoU for square
        bounding boxes of varying size. A single-axis shift is applied to
        the predicted box while the ground-truth box remains fixed. At
        $\delta = 2$ pixels, a $16 \times 16$ box drops to
        $\mathrm{IoU} = 0.78$ while a $64 \times 64$ box retains
        $\mathrm{IoU} = 0.94$, illustrating why small-object detection is
        disproportionately sensitive to localisation error. The dashed line
        marks the standard $\mathrm{mAP}_{50}$ threshold.}
    \label{fig:iou_degradation}
\end{figure}
 
 
\subsection{Strategies for Small-Object Detection}
\label{subsec:background_small_object_strategies}
 
Several strategies have been proposed to address these difficulties.
Multi-scale detection heads, as used in FPN-based architectures, are the most
widely adopted architectural response; some methods extend this with
additional high-resolution prediction scales or dilated
convolutions~\cite{lin2017feature}. At the data level, augmentation
techniques such as copy-pasting small object instances into new training
locations improve recall on under-represented size
categories~\cite{kisantal2019augmentation}, while inference-time tiling
increases effective resolution at the cost of higher computation.
 
A complementary approach is to train a dedicated detector whose capacity,
input resolution, and confidence thresholds are tuned specifically for the
small-object class. This avoids the class-imbalance problem inherent in
joint training and allows the operating point to be optimised independently.
In particular, operating at a low confidence threshold $\tau$ maximises
recall at the cost of increased false positives — a trade-off that can be
managed by downstream temporal filtering rather than within the detector
itself~\cite{Gualtieri2023}.
 
 
\subsection{Temporal Filtering of Ball Candidates}
\label{subsec:background_temporal_filtering}
 
When a detector operates at a low confidence threshold, the resulting
candidate set at each frame contains both the true ball and spurious
detections. The general form of this set at frame $t$ is
\begin{equation}
    C_t = \left\{\bigl(\mathbf{b}_t^{(j)},\, s_t^{(j)}
           \bigr)\right\}_{j=1}^{N_t},
    \label{eq:ball_candidates}
\end{equation}
where $\mathbf{b}_t^{(j)}$ is a candidate location and $s_t^{(j)}$ its
confidence score.
 
Temporal coherence provides a principled basis for disambiguation. Because
the ball follows a physically continuous trajectory, its inter-frame
displacement is bounded even under rapid motion. Two families of filtering
exploit this property. Motion-model approaches, such as the Kalman filter
described in Section~\ref{subsec:background_tracking_by_detection}, predict
the ball's next position using an explicit dynamical model and select the
closest candidate. These are effective when the assumed model holds, but can
diverge under the abrupt accelerations from kicks, deflections, and rebounds
that are routine in football. An alternative family enforces only that
inter-frame displacement remains below a physically plausible bound,
discarding candidates that would imply impossible ball speeds regardless of
confidence. This sacrifices predictive power during smooth motion but is more
robust to the sharp trajectory changes characteristic of ball dynamics.
 
The choice between these families, and the specific instantiation used in
this project, is discussed in Chapter~\ref{ch:methodology}.
Chapter~\ref{ch:evaluation} reports ball detection performance separately
from the general object detector.

\subsection{Dedicated Ball Detector Training}
\label{subsec:train_ball}

The dedicated ball detector was initialised from the pretrained
\texttt{yolov8x.pt} checkpoint and fine-tuned for 150 epochs at input
resolution $1280 \times 1280$, with a batch size of 8, early-stopping
patience of 30 epochs, and the Ultralytics \texttt{auto} optimiser
resolving to AdamW with a learning rate of $2 \times 10^{-3}$.
Augmentation settings mirrored those used for the generic detector,
with \texttt{mixup} and \texttt{copy\_paste} disabled. Training was
carried out on an NVIDIA~A100-80GB GPU on the University of Manchester
CSF3 HPC facility, with mixed-precision (AMP) enabled throughout, and
the full run took approximately 109 minutes of wall-clock time. The
full training log and per-epoch \texttt{results.csv} are retained under
\texttt{artifacts/ball\_detection\_model\_yolov8-x/}, allowing the
training curves to be reproduced exactly.

\paragraph{Choice of the larger variant.} The ball detector uses the
\texttt{yolov8x} variant (68.1\,M parameters) rather than the
\texttt{yolov8m} variant used for the generic detector. The motivation
is that the ball is a small, fast-moving object whose appearance offers
very little discriminative signal per pixel, and a higher-capacity
backbone is better able to extract useful features from the few pixels
on target. Because the dedicated detector runs only once per frame on
the same input as the generic detector, and because the ball pipeline
does not participate in per-frame tracking, the additional inference
cost of the larger variant is acceptable within the overall runtime
budget.

\subsection{Pitch Keypoint Detector Training}
\label{subsec:train_keypoints}

The pitch keypoint model was initialised from the pretrained
\texttt{yolov8x-pose.pt} checkpoint and fine-tuned for 500 epochs at
input resolution $640 \times 640$, with a batch size of 48, early-stopping
patience of 100 epochs, and the Ultralytics \texttt{auto} optimiser.
Training was carried out on an NVIDIA~A100-40GB GPU in a Google Colab
environment, with mixed-precision enabled throughout, and the full run
took approximately 45 minutes of wall-clock time. The full training log
and per-epoch \texttt{results.csv} are retained under
\texttt{artifacts/pitch\_keypoint\_detection\_model/}.

\paragraph{Mosaic disabled for keypoint training.} One departure from the
default augmentation used elsewhere is that mosaic augmentation was
explicitly disabled. Mosaic composes four images into a single training
image by tiling; for bounding-box detection this is helpful (it
increases the number of objects seen per batch and encourages
context-invariance), but for keypoint tasks the tiling disrupts the
geometric relationships between keypoints that the model must learn,
since keypoints near the tile boundaries may be cropped or relocated in
ways that do not correspond to any real camera viewpoint. Horizontal
flip was retained because the keypoint layout defines an explicit
left--right symmetry via \texttt{flip\_idx}; vertical flip and
perspective augmentation were disabled for the same geometric-integrity
reasons.

\paragraph{Deployment path.} The trained weights were exported and
deployed to Roboflow for hosted inference, and the pipeline consumes the
keypoint model through Roboflow's hosted inference API rather than
loading the local weights directly. The rationale for this deployment
choice is explained in Section~\ref{sec:pitch_registration}, which
discusses the pitch registration stage that consumes this model's
output.

\section{Detection and Tracking}
\label{sec:detection_tracking}

The first operational stage of the pipeline detects the visual entities required
for downstream football analysis and assigns persistent identities to players
across frames. This stage is critical because later components, including team
identification, pitch-space projection, possession estimation, heatmaps, and
offside candidate detection, all depend on the reliability of the detections
and tracks produced here.

\subsection{Main Object Detection}
\label{subsec:main_object_detection}

The main detector is a YOLOv8m object detection model trained to recognise four
classes: players, goalkeepers, referees, and the ball. During inference, each
video frame is passed through the detector at an image size of 1280 pixels. The
runtime confidence threshold is set to 0.2 and the IoU threshold is set to 0.5.
These values were chosen to retain sufficient detections for the tracker while
still removing low-confidence false positives.

The detector output for each frame consists of a set of bounding boxes, class
labels, and confidence scores. These detections are converted into
\texttt{supervision} detection objects so that they can be passed consistently
between the object detection, tracking, annotation, and tactical analysis
modules. Preserving this intermediate representation also makes it easier to
inspect and evaluate the behaviour of individual pipeline stages.

Although the main detector includes a ball class, the ball is substantially
harder to detect than players because it occupies very few pixels and is often
blurred or occluded. For this reason, the main detector is used primarily for
players, goalkeepers, and referees, while ball localisation is strengthened
using a separate dedicated detector.

\subsection{Dedicated Ball Detection and Filtering}
\label{subsec:dedicated_ball_detection_filtering}

A dedicated YOLOv8x ball detector is applied to each frame to improve the
reliability of ball localisation. This design decision was made because errors
in ball detection propagate directly into possession, pass, and offside
analysis. A missed or incorrect ball location can cause the system to assign
possession to the wrong player, miss a pass transition, or trigger an incorrect
offside candidate event.

The ball detector is run with a low initial confidence threshold
(\texttt{ball\_conf = 0.05}) so that weak ball candidates are not discarded too
early. Candidate detections are then filtered temporally. A ball candidate is
accepted only if it is sufficiently confident or spatially consistent with the
previous accepted ball position. In particular, the pipeline uses a maximum
jump threshold of 80 pixels and a minimum stronger-confidence threshold of
0.25. This prevents isolated low-confidence detections far from the previous
ball position from being selected as the ball.

When multiple ball candidates are present, the system selects the candidate
that is most consistent with the recent ball position. This filtering strategy
does not solve all cases of ball occlusion or fast motion, but it reduces the
effect of isolated false positives and produces a more stable ball trajectory
for downstream tactical reasoning.

\subsection{Multi-object Tracking}
\label{subsec:multi_object_tracking}

Player tracking is performed using tracking-by-detection. In each frame, the
main YOLO detector supplies bounding boxes to a tracker, which assigns a
persistent track identifier to each detected player. The default tracker used
in the pipeline is ByteTrack, with BoT-SORT available as an alternative
configuration. The tracker is selected through the runtime tracker
configuration, allowing the same pipeline to be evaluated with different
tracking algorithms.

ByteTrack was selected as the default tracker because it is designed to use
both high-confidence and lower-confidence detections during association. This
is useful in broadcast football footage, where players are frequently
partially occluded and their detection confidence may temporarily fall even
when they remain visible. By retaining lower-confidence detections for a second
association step, ByteTrack can reduce unnecessary track fragmentation in
crowded scenes.

The tracker returns detections with associated track identifiers. These track
identifiers are preserved in the pipeline and are used by later stages to
accumulate player positions, smooth team labels, generate heatmaps, and compute
player-level statistics. Detections without valid track identifiers are not
used for player-level temporal statistics, since they cannot be linked
reliably across frames.

\subsection{Track Handling and Failure Cases}
\label{subsec:track_handling_failure_cases}

The tracking stage is vulnerable to several common failure cases. Occlusion can
cause a player to disappear temporarily, leading to a broken track. Similar
player appearance can cause identity switches, particularly when players cross
or cluster around the ball. Camera motion can also affect the apparent movement
of detections and make association more difficult.

The pipeline mitigates these issues in two ways. First, the tracker itself
uses temporal association to preserve identities across short interruptions.
Second, downstream stages avoid relying on a single frame wherever possible.
For example, team labels are smoothed across a fixed track history, and
movement statistics include a maximum-speed gate to reduce the effect of
spurious projected movements.

Nevertheless, tracking errors cannot be fully eliminated at this stage. A
fragmented or incorrect track can affect player heatmaps, distance estimates,
team-level possession, and offside candidate detection. For this reason, the
evaluation considers both the component-level behaviour of the tracker and the
effect of tracking errors on the integrated pipeline.

\section{Team Identification}
\label{sec:method_team_identification}

After player detections have been assigned track identifiers, the next stage is
to infer the team membership of each tracked player. This is required for
team-level outputs such as possession statistics, pass events, offside
candidate detection, and team-coloured visualisations. The system performs
team identification without match-specific manual labels by fitting an
unsupervised classifier from player crops sampled from the input video.

\subsection{Warm-up Sampling and Player Cropping}
\label{subsec:warmup_sampling_player_cropping}

Team identification begins with a warm-up phase at the start of each video.
During this phase, frames are sampled from the first 20 seconds of footage using
a stride of 30 frames. The main detector is applied to these sampled frames, and
only detections classified as players are retained. Very small crops are
discarded using a minimum bounding-box size of 35 by 35 pixels, since such
detections usually contain too little visual information for reliable team
assignment.

For each retained player detection, the system extracts a torso crop rather
than using the full bounding box. The crop is taken from approximately 15\% to
65\% of the bounding-box height. This focuses the representation on the shirt
region, which usually contains the strongest team-specific visual signal, while
reducing noise from shorts, legs, grass, and nearby players. A maximum of 800
warm-up crops is used, and at least 50 crops are required before the classifier
is fitted.

\subsection{Embedding and Clustering}
\label{subsec:embedding_clustering}

The retained torso crops are used to fit a team classifier. The classifier
extracts visual embeddings from each crop using a SigLIP-based image encoder,
then reduces the embedding dimensionality using UMAP and clusters the reduced
representations using K-means with \(k=2\). The two clusters correspond to the
two outfield teams.

This approach was selected because it avoids requiring labelled team examples
for every new match. A supervised team classifier would need new annotations
whenever kits, lighting conditions, competitions, or broadcast styles changed.
By fitting the classifier from the input video itself, the system can adapt to
the visual appearance of the teams in the current match.

During the per-frame pipeline, each tracked player crop is passed through the
same embedding and clustering pipeline to obtain a predicted team label. The
output is a binary team assignment for outfield players. These assignments are
then stabilised using temporal smoothing before being used by downstream
analytics.

\subsection{Temporal Smoothing and Role Handling}
\label{subsec:temporal_smoothing_role_handling}

Frame-level team predictions can fluctuate because of occlusion, motion blur,
partial crops, lighting variation, or players turning away from the camera. To
reduce this instability, the system applies track-level majority-vote smoothing.
For each track identifier, the most recent team predictions are stored in a
fixed-length history of 30 predictions. The smoothed team label is then taken as
the majority label within this history.

This design reduces the effect of isolated incorrect predictions while still
allowing the team label to update if a track was initially misclassified.
Smoothing is especially important because team labels are used in later
components where a single-frame error can affect possession, pass, or offside
logic.

Goalkeepers and referees require separate handling. Referees are assigned to a
non-team class because they do not contribute to team possession or offside
analysis. Goalkeepers are detected as a separate object class and are assigned
to the team whose outfield-player centroid is nearest in image space. This
spatial rule is used because goalkeeper kits often differ from the outfield
players' kits, making appearance-based clustering less reliable for this role.

The resulting representation assigns each detection either to team 0, team 1,
or a non-team class. This representation is used consistently by the
visualisation, possession, pass, and offside modules.

\section{Pitch Registration}
\label{sec:method_pitch_registration}

Pitch registration maps image-space detections from the broadcast frame onto a
canonical football pitch. This stage is required because image coordinates are
affected by camera position, zoom, and perspective distortion. Tactical outputs
such as heatmaps, speed, distance, possession proximity, and offside candidate
detection therefore need to be computed in pitch space rather than directly in
the broadcast image.

\subsection{Pitch Keypoint Detection}
\label{subsec:pitch_keypoint_detection}

Pitch landmarks are detected using a YOLOv8x-pose model trained to localise 32
canonical pitch keypoints. For each processed frame, the model predicts a set
of keypoint coordinates and confidence scores. Keypoints with confidence below
0.5 are discarded before homography estimation. This filtering step reduces the
effect of uncertain keypoint predictions, which can otherwise produce unstable
or incorrect pitch transformations.

A homography is estimated only when at least six valid keypoints are available.
Although four point correspondences are theoretically sufficient to estimate a
homography, requiring more than four points makes the transformation less
dependent on any single detected landmark. Frames with too few reliable
keypoints reuse the most recent valid transformation where possible, rather
than forcing an unstable new estimate.

\subsection{Homography Estimation and Coordinate Transformation}
\label{subsec:homography_coordinate_transformation}

For each valid set of pitch keypoints, the system estimates a homography
between the detected image-space landmarks and their corresponding locations on
a canonical pitch model. The homography provides a projective transformation
from image coordinates to pitch coordinates. Once this transformation is
available, detected object positions can be expressed in pitch space.

For players, goalkeepers, and referees, the image-space position is taken as
the bottom-centre point of the bounding box, since this approximates the point
where the player contacts the ground. For the ball, the centre of the bounding
box is used. These points are then transformed into pitch coordinates using the
estimated homography.

The pitch coordinate system is represented in centimetres, with a pitch length
of 12,000 cm. Using metric-like pitch units allows later stages to express
distance thresholds and spatial rules in interpretable terms. For example, the
possession and offside modules use distances in centimetres rather than pixel
distances, making the thresholds less dependent on camera zoom.

\subsection{Caching and Robustness Measures}
\label{subsec:caching_robustness_measures}

Estimating a new pitch transformation on every frame is computationally
expensive and can also introduce visual jitter when keypoint predictions vary
slightly between consecutive frames. To reduce this problem, the pipeline
recomputes the pitch transformation every 15 frames and caches the most recent
valid transformation between updates.

This stride-cached design is a compromise between accuracy, stability, and
runtime. Updating the homography too rarely can make the transformation lag
behind camera motion, while updating it every frame can amplify keypoint noise.
A stride of 15 frames provides regular updates while reducing unnecessary
recomputation.

Pitch registration remains one of the most important sources of downstream
error. If the homography is inaccurate, then all pitch-space outputs derived
from it may be affected, including heatmaps, speed and distance estimates,
possession proximity, and offside geometry. For this reason, registration
quality is inspected both visually through bird's-eye outputs and quantitatively
where keypoint validation metrics are available.

\section{Tactical Output Generation}
\label{sec:tactical_output_generation}

Once detections have been tracked, assigned team labels, and transformed into
pitch coordinates, the system generates tactical outputs from the resulting
structured representation. These outputs are intended to make the broadcast
video more analytically useful by converting low-level detections into visual
summaries, player statistics, team possession estimates, pass events, and
candidate offside situations.

\subsection{Bird's-eye Visualisation}
\label{subsec:birdeye_visualisation}

The bird's-eye visualisation represents the detected players, goalkeepers,
referees, and ball on a canonical top-down pitch. For each frame with a valid
pitch transformation, the image-space object positions are projected into pitch
coordinates and rendered on the pitch model. Players are coloured according to
their inferred team labels, referees are shown as a separate non-team class,
and the ball is rendered using its filtered pitch-space position when
available.

This visualisation provides an interpretable way to inspect whether the
detection, team assignment, and pitch registration stages are behaving
coherently. It is also used to generate side-by-side videos, where the original
broadcast frame and the corresponding pitch-space representation are displayed
together. This makes it easier to identify errors such as incorrect team
labels, unstable homographies, or ball locations that do not match the
broadcast footage.

\subsection{Heatmaps, Speed and Distance}
\label{subsec:heatmaps_speed_distance}

Player heatmaps are generated by accumulating each tracked player's pitch-space
positions over time. The pitch is divided into a fixed grid of
\(480 \times 280\) cells, and each valid player position contributes to the
corresponding grid location. Heatmaps are generated only when at least 40 valid
samples are available for a track, reducing the likelihood of producing
misleading visualisations from short or fragmented tracks.

To improve readability, the accumulated heatmap is smoothed using a Gaussian
blur with kernel size 31 and a gamma correction of 0.22. The final heatmap is
saved both as an image and as a raw numerical array, so that the visual output
can be inspected while the underlying positional distribution remains
available for further analysis.

Speed and distance estimates are computed from changes in player pitch-space
position over time. Consecutive valid positions for each track are used to
estimate displacement, which is accumulated to produce total distance
travelled. Speed is derived from displacement and frame timing. Since small
errors in pitch registration can produce unrealistically large apparent jumps,
the system applies a maximum-speed gate of 40 km/h. Movements above this
threshold are treated as noise and excluded from the accumulated statistics.

\subsection{Possession and Pass Detection}
\label{subsec:possession_pass_detection}

Possession is estimated using the pitch-space distance between the filtered
ball position and nearby players. For each frame, the system identifies the
player closest to the ball. A player is considered a possession candidate only
if the distance to the ball is below 350 cm. To reduce noise from brief
misdetections or transient ball movements, possession must be stable for at
least three consecutive frames before being confirmed.

Team possession is then obtained from the confirmed player's team label. If no
player satisfies the proximity condition, the frame is treated as having no new
confirmed possession event. This conservative design reduces the risk of
assigning possession during periods when the ball is airborne, occluded, or
incorrectly detected.

Pass events are detected from stable changes in possession. A pass is recorded
when confirmed possession changes from one player to another in a temporally
stable way. This rule-based definition is intentionally simple: it is designed
to identify likely possession transfers rather than to provide a complete
semantic classification of football actions. As a result, the pass output is
best interpreted as a set of candidate pass events that require evaluation
against manually inspected clips.

\subsection{Offside Candidate Detection}
\label{subsec:offside_candidate_detection}

Offside candidate detection is performed in pitch space using the detected
players, inferred team labels, ball position, and estimated attacking
direction. The attacking direction is inferred automatically from accumulated
team \(x\)-centroids once at least 30 valid team-position samples are
available, rather than being manually specified for each video.

For each frame with sufficient information, the system estimates the offside
line from the second-last defender's pitch-space position. If only one defender
is available, a fallback line is computed using the available defensive player,
although this case is less reliable. An attacker is treated as a candidate
offside player if they are beyond the defensive line by more than a 30 cm
margin at the relevant moment and are spatially close enough to the ball event
context to be considered involved in play.

The output of this module is not intended to replicate full official offside
judgement. The official law depends on contextual factors such as the exact
moment the ball is played, active involvement, deliberate play by defenders,
and body-part eligibility. The system instead detects candidate offside
situations under simplified geometric assumptions. Candidate events are saved
as structured JSON records and visualised using an overlay for a fixed display
duration of 50 frames, allowing them to be inspected during evaluation.

\section{Evaluation Methodology}
\label{sec:evaluation_methodology}

The evaluation was designed to assess both the individual components of the
pipeline and the behaviour of the integrated system. This distinction is
important because strong component-level performance does not necessarily imply
that the final tactical outputs are reliable. For example, a detector may
achieve high validation accuracy while still missing the ball in key moments,
or a pitch registration model may perform well on isolated frames while
producing unstable transformations during camera motion. The evaluation
therefore considers not only model-level metrics, but also the extent to which
the complete pipeline produces coherent and useful football analysis outputs.

\subsection{Component-level Evaluation}
\label{subsec:component_level_evaluation}

The first level of evaluation assesses the supervised models used by the
pipeline. The main object detector, dedicated ball detector, and pitch keypoint
detector are evaluated using their validation or test splits, with metrics
appropriate to each task.

For the object detection models, performance is measured using precision,
recall, mAP@50, and mAP@50--95. These metrics assess both whether the relevant
objects are detected and how accurately their bounding boxes are localised. The
dedicated ball detector is evaluated separately because ball localisation is a
known bottleneck for downstream possession, pass, and offside analysis.

For the pitch keypoint model, evaluation considers both bounding-box and
keypoint performance where available. The keypoint metrics are particularly
important because pitch registration depends on the geometric accuracy of the
detected landmarks rather than only on whether the pitch itself is detected.

Tracking is evaluated by comparing the stability and continuity of player
tracks across representative clips. Where manual annotations are available,
track fragmentation, identity switches, and track continuity are assessed
directly. Where dense tracking ground truth is not available, the tracker is
evaluated through visual inspection, track-count consistency, and its effect on
downstream outputs such as heatmaps and distance estimates.

\subsection{End-to-end Pipeline Evaluation}
\label{subsec:end_to_end_pipeline_evaluation}

The second level of evaluation assesses the complete pipeline on broadcast
football clips. This evaluation focuses on whether the system produces coherent
outputs after all components have been combined. The main outputs considered
are annotated broadcast videos, bird's-eye visualisations, side-by-side videos,
heatmaps, statistics files, and offside event records.

End-to-end evaluation is performed using representative clips containing common
broadcast conditions, including camera panning, zooming, player occlusion, ball
movement, and changes in pitch visibility. The outputs are inspected to assess
whether detected entities remain visually consistent, whether team labels are
stable, whether pitch-space projections remain aligned with the broadcast view,
and whether the generated statistics are plausible.

Where manual labels are produced, tactical outputs are evaluated against
manually inspected ground truth. Possession estimates are compared with the
observed player or team in control of the ball, pass events are compared with
manually identified possession transfers, and offside candidates are compared
with visible attacking situations in the clip. This provides a more meaningful
assessment of tactical usefulness than model-level metrics alone.

\subsection{Ablation Studies}
\label{subsec:ablation_studies}

Ablation studies are used to evaluate the contribution of key design decisions.
Each ablation changes one component or configuration while keeping the rest of
the pipeline fixed, allowing the effect of that design choice to be isolated.

The planned ablations are:

\begin{itemize}
    \item \textbf{Dedicated ball detector.} The pipeline is compared with and
    without the dedicated ball detector to determine whether the specialised
    model improves possession, pass, and offside outputs.

    \item \textbf{Tracker choice.} ByteTrack and BoT-SORT are compared on the
    same clips to assess differences in track continuity, identity stability,
    and downstream statistics.

    \item \textbf{Team-label smoothing.} Raw frame-level team predictions are
    compared with track-level majority-vote smoothing to assess whether
    smoothing reduces label instability.

    \item \textbf{Pitch registration stride.} Different homography update
    intervals are compared to measure the trade-off between runtime,
    projection stability, and responsiveness to camera motion.

    \item \textbf{Speed filtering.} Distance and speed estimates are compared
    with and without the maximum-speed gate to determine how much unrealistic
    movement is introduced by registration noise.
\end{itemize}

These ablations are included because the project contains several design
choices that could otherwise appear arbitrary. Comparing alternatives makes it
possible to justify the final configuration and identify which components have
the greatest effect on end-to-end reliability.

\subsection{Runtime Evaluation}
\label{subsec:runtime_evaluation}

Runtime evaluation measures the practical cost of processing broadcast video.
The system records total processing time and, where possible, the time spent in
major pipeline stages such as detection, ball detection, pitch registration,
team assignment, rendering, and tactical output generation.

Runtime is reported as processing time per frame and effective frames per
second. Additional comparisons are made for configurations that change runtime
substantially, such as different pitch registration strides or optional
bird's-eye and side-by-side rendering. This allows the evaluation to distinguish
between methods that improve output quality and methods that are too expensive
for practical use.

The aim is not necessarily to achieve real-time performance, since the project
prioritises analytical quality and reproducibility. However, runtime remains an
important non-functional requirement because a system that is too slow to run on
complete clips would have limited practical value.

\subsection{Error Analysis}
\label{subsec:error_analysis}

Error analysis is used to examine where the pipeline fails and how errors
propagate between stages. This is necessary because the final tactical outputs
depend on several earlier components. A missed ball detection can affect
possession and pass detection; an identity switch can distort heatmaps and
distance estimates; an incorrect team label can affect possession and offside
logic; and an unstable homography can corrupt all pitch-space measurements.

The evaluation therefore records representative failure cases and groups them
by cause. The main categories considered are missed or false detections, ball
tracking errors, track fragmentation, team-label switches, pitch registration
failures, and tactical inference errors. For each category, the analysis
identifies the likely cause, the downstream effect, and any mitigation used in
the pipeline.

This error-focused evaluation is important because the project is an integrated
system rather than a single model. The objective is not only to report whether
the outputs are correct, but also to explain why they succeed or fail under
different broadcast conditions. This provides the basis for the critical
evaluation in Chapter~\ref{ch:evaluation}.

\section{Implementation and Reproducibility}
\label{sec:implementation_reproducibility}

The pipeline was implemented in Python, using a modular code structure so that
individual stages could be configured, tested, and replaced independently. The
main entry point is \texttt{src/track\_video\_supervision.py}, which parses the
runtime configuration and calls the pipeline orchestration code in
\texttt{src/pipeline/run.py}. This organisation separates high-level execution
from the component-specific modules used for detection, team identification,
pitch registration, visualisation, statistics, and offside detection.

\subsection{Software Environment}
\label{subsec:software_environment}

The implementation uses Python 3.11. The main libraries are Ultralytics for
YOLO model training and inference, Supervision for detection handling and video
annotation utilities, OpenCV for image processing and video writing, NumPy for
numerical operations, scikit-learn and UMAP for clustering-related operations,
and Hugging Face Transformers for the SigLIP-based team embedding model. The
Roboflow inference tools are used for the pitch model integration, and the
Roboflow sports library is used for the team classification pipeline.

The project dependencies are recorded in \texttt{requirements.txt}. In addition,
the Roboflow sports library is installed as an editable dependency from its
source repository. The environment also requires a Roboflow API key and field
model identifier, which are specified through environment variables. An example
environment file is provided to document the required variables without exposing
private credentials.

\subsection{Configuration and Model Weights}
\label{subsec:configuration_model_weights}

The pipeline is controlled through runtime parameters rather than hard-coded
settings. Important configuration values include the detector image size,
detection confidence threshold, IoU threshold, tracker type, pitch registration
stride, keypoint confidence threshold, ball filtering thresholds, team
smoothing window, heatmap settings, and offside detection parameters.

The default inference configuration uses an image size of 1280 pixels, detector
confidence threshold of 0.2, IoU threshold of 0.5, and ByteTrack as the tracker.
The team classifier samples the first 20 seconds of video with a stride of 30
frames and applies a 30-frame smoothing window to team predictions. Pitch
registration is updated every 15 frames, using keypoints with confidence at
least 0.5 and requiring at least six valid keypoints before estimating a
homography.

The trained model weights are stored separately from the source code. The
required weights are the main object detector
\texttt{models/object\_detection/best.pt}, the dedicated ball detector
\texttt{models/ball\_detection/best.pt}, and the pitch keypoint detector
\texttt{models/pitch\_keypoints/best.pt}. To reproduce the full system, these
weights must either be supplied with the project artefacts or regenerated using
the documented training scripts and notebooks.

\subsection{Running the Pipeline}
\label{subsec:running_pipeline}

The pipeline can be executed from the command line using the provided run
scripts. The standard execution path processes an input video, writes an
annotated output video, and optionally generates bird's-eye videos,
side-by-side videos, heatmaps, statistics files, pitch debug videos, and
offside event records. The main generated outputs are written to the
\texttt{outputs/} directory.

For each input video, the core output is an annotated video showing detections,
track identifiers, team labels, the ball marker, and offside overlays where
enabled. Optional outputs include a bird's-eye video, a side-by-side
broadcast-and-pitch view, JSON statistics, JSON offside-event records, and
per-player heatmap files. The statistics output records team possession,
passes, player speed estimates, and distance travelled, while the heatmap
directory stores both image files and raw numerical arrays.

This output structure was chosen to support both visual inspection and later
evaluation. Videos make it possible to inspect whether the integrated pipeline
is behaving plausibly, while JSON and numerical outputs allow quantitative
comparison with manual labels and ablation results.

\subsection{Reproducibility Limitations}
\label{subsec:reproducibility_limitations}

Several limitations affect exact reproducibility. First, the trained model
weights are external artefacts and are not stored directly inside the source
code repository. Reproducing the system therefore requires either access to the
trained weights or re-training the models from the documented datasets and
training configuration.

Second, some datasets and hosted models are accessed through Roboflow services,
so reproduction depends on access to the relevant workspaces, dataset versions,
and API credentials. Third, although YOLO training used deterministic settings
and a fixed seed where supported, the runtime team classifier is fitted from
sampled video crops and may vary if the underlying embedding, UMAP, or
clustering behaviour is not fully deterministic.

Finally, the current implementation is primarily an experimental research
pipeline rather than a fully packaged software product. It provides scripts,
configuration parameters, model artefact locations, and documented outputs, but
does not include a complete automated unit-test suite. This limitation is
addressed in the evaluation through component-level validation, visual
inspection, ablation studies, and end-to-end testing on representative clips.

\section{Chapter Summary}
\label{sec:methodology_summary}

This chapter described the methodology used to construct the proposed
broadcast football video analysis pipeline. The system was designed around a
set of functional and non-functional requirements, with the central objective
of producing tactical outputs from a single broadcast video without relying on
commercial tracking infrastructure.

The methodology used a modular architecture in which object detection, ball
detection, multi-object tracking, team identification, pitch registration, and
tactical output generation are implemented as separable stages. This structure
allows each component to be configured and evaluated independently, while still
supporting end-to-end analysis of the complete pipeline.

The chapter also described the datasets, model training procedures, runtime
configuration, and reproducibility measures used by the system. Particular
attention was given to design decisions that affect downstream reliability,
including the use of a dedicated ball detector, track-level team-label
smoothing, stride-cached pitch registration, and pitch-space rules for
possession, pass, and offside candidate detection.

The following chapter reports the results produced by this methodology,
including model-level validation results, pipeline outputs, tactical
statistics, visualisations, and runtime measurements. Chapter~\ref{ch:evaluation}
then evaluates these results against the requirements and success criteria
defined in this chapter.
